# 0025: A goal ends with a report the code puts together, and agents' claims are checked against facts where the code can check them

- Status: Accepted
- Date: 2026-11-26
- Related: [0004](0004-project-memory-on-disk.md) (project memory), [0007](0007-local-only-user-messages.md) (what only a local model saw), [0014](0014-goal-mode-confirmed-goal-card.md), [0015](0015-goal-mode-fresh-review.md), [0017](0017-goal-mode-research-and-meeting-first.md), [0018](0018-goal-mode-task-cards.md), [0019](0019-goal-mode-call-estimate-and-limit-wait.md), [0022](0022-goal-mode-records-and-block-allow-list.md), `server/report.js` (`buildReport`, `reportText`, `reportLocal`, `unverifiedLines`), `server/proof.js` (`gitState`, `gitDiffNames`, `changedSet`, `proofCheck`), `server/mission.js` (`meetingRecord`, `recordMeeting`, `planEstimate`, `tailClaims`, `tailFiles`, `userLine`, `reviewPrompt`, `resumePoint`), `public/js/office/meeting.js` (`conclusionParts`), `server/orchestrator.js` (`#missionEnd`, `#report`, `reportMemory`, `#missionMsgLines`, `#missionRun`, `#planStage`, `#planCheck`, `#missionWork`, `#proofSnap`, `#proofCheck`, `#reviewStage`, `#recall`), `server/memory.js` (`hide`, `search`, `stats`), `server/store.js` (`#fixStale`), `server/index.js` (`POST /api/sessions/:id/report/:mid/memory`), `public/js/views/mission.js` (`ReportCard`, `PlanCard`, `MissionGate`), `public/js/views/memory.js` (`MemoryPage`, `MemoryBadge`), `public/js/stage-model.js` (`goalEndWord`), `test/goal-report.test.js`, `test/prompt-size.test.js`, `test/fake-cli/fake-claude.js`

## Revision (2026-11-26, with [0030](0030-goal-run-records-retry-and-flow-map.md))

The report's failure kinds count `transient` too ([0030](0030-goal-run-records-retry-and-flow-map.md)): the automatic retry after a temporary outage and outage errors before the error wait. A goal's run can now also be exported as one JSON file (format `office-crew-goal-run`, version 1, with the report's facts but not its memory state), with secrets and paths masked and text only when asked for; that record describes the format.

## Context

A goal ended with a status chip, the criteria table and a progress log of up to 200 lines. Nothing put together what happened: how many calls went where, what the user decided along the way, what was never checked, which failures happened. The pieces that matter were scattered over the log, the mission fields and message marks. Meeting conclusions were free text the code only passed on. A task card's "Changed files" closing line (0018) was taken on trust. The call estimate on the goal card (0019) was made before the plan existed, so a plan with more cards than expected ran into the call cap midway. And project memory (0004) got nothing from a goal except its messages. Outside sources pointed the same way: a closing report filled from facts the system recorded (with the agents' own summary kept apart), drafts kept apart from accepted records, and a size check on fixed prompt text so it doesn't grow unnoticed.

## Options

1. Have an AI write the closing summary. It costs a call, and a summary that says "all done" can't be told from the facts it should be checked against.
2. A report built by code from records that already exist, agents' text kept apart and marked; conclusion lines read from the format the conclusion prompt already asks for; changed files compared with git as a warning; the estimate redone after the plan with the shared function; the report going into memory only when the user adds it.
3. As 2, but treat a card whose files didn't change as failed. Files git ignores and paths outside the work folder would fail work that was done.

## Decision

Option 2.

- **Report card** (`buildReport`, `#report`, no AI call): when a goal's work run ends `done`, `accepted` or `stopped`, one message `{ role: 'proposal', kind: 'report', status: 'done', text: '', missionId, end, goal, from, to, calls: { used, cap }, estimate, answers, answerFails, criteria, user, userMore, unverified, fails, routes, logCut, meetings, files, filesState, memFolder, local? }` and `mission.reportMsgId`. Not for a goal cut by closing the app (`cut` is alive), not for a goal closed before it was confirmed, and not for a cut goal that is discarded; a cut goal that is continued and then ends gets it once. Facts first: the end state (named as the flow stage's end flag names it, `goalEndWord`), time from confirming to the end, actual calls next to the estimate of 0019, answers per kind by the existing message marks (goal, research including research during a meeting, meeting turns, plan, task cards, work stages, check; retries inside an answer are not separate; answers that ended in an error or a stop count too, since they used a call, and how many of them did is shown apart as `answerFails`), each criterion's last verdict, what the user chose, from the progress-log lines the code marks `by: 'user'` where it records a user's choice (confirming the goal card and what was chosen on it, the answers in the question boxes, extra instructions, the first line of each continue; the code's own notes, such as who reviews or an automatic continue after the reset time, are not marked; a log with no marks at all, from an older version, is read as before: confirm and answer lines, and note and continue lines that point to a message), what was not checked (criteria `unknown` or never judged, research questions that ended empty, failed or skipped, cards left as gaps, blocked or skipped and why, cards whose claimed files didn't change, skipped stages of the last work run, usage-limit stops, one per quota line; continuing a goal cut at a limit wait asks again without writing another quota line, as 0022 does for error and blocked lines), the failure kinds of 0022 counted from the log (a verdict that ended at the usage limit leaves a quota line and a review line, both `outside`; the report counts that event once, by its quota line), and the number of answers whose routing was unusual (`route` lines). The changed files are filled in afterwards the same way as the check's material (`git status`, 50 paths, the count of the rest; uncommitted changes, which can include changes from before the goal). Agent-written text is marked "written by an agent" and cut: a criterion's evidence to 200 characters, a meeting's decision and remaining disagreement as stored, and the paths a card wrote under "Changed files" in what was not checked. The card is collapsed to one line by default (a button with `aria-expanded` and `aria-controls`; the body is always there and hidden while collapsed), in four languages. If putting the report together throws, the goal stays ended as it is, the session is saved and the run goes on to the next queued message, and the conversation gets one line ("Couldn't make the goal report"). A report whose changed files were still being asked when the app closed shows them as not available when the session is read again (`filesState: 'none'`). The progress log gets no line for it, so the end line stays last.
- **Meeting conclusions** (`conclusionParts`, `meetingRecord`, `recordMeeting`): the conclusion prompt already asks for "Decision / Why / Remaining disagreement / Dropped options / Next steps" lines (the village board already read the decision line). The reader of that line now reads all five heads in the four languages (bold or numbered, a value on the same line or indented lines under it, "none" in each language as an empty list, also as "(none)", "None.", "없습니다", "なし", "无" or "没有"). Heads are read only from lines that aren't indented (an indented "Why:" inside a list item stays part of that item), and only the last group of heads counts: walking back from the end until a head repeats. So a summary with a "Decision:" line above the conclusion doesn't win; the village board takes the last decision line the same way. When a goal meeting (the pre-work meeting or a team meeting stage in a goal's work run) concludes, `mission.meetings` gets `{ prep: true | stageIndex, msgId, decision, reasons[], dissent[], dropped[], next[] }` (each value one line, 300 characters, lists of 5, at most 20 meetings). A conclusion without those lines is kept as it is and the fields stay empty; nothing is made up. What goes to the next steps is unchanged (the whole conclusion as reference). No prompt text was added.
- **Changed files of a task card** (`gitState`, `changedSet`, `proofCheck`): for a card step with build or write cards, the code takes the work folder's git state before the step (top-level prefix, `HEAD`, `git status --porcelain -z` with each path's modification time and size) and after it (and the files of any commits made in between). The "Changed files" items (split at lines and commas, full-width ones included) are read as paths (`tailClaims`): a markdown link's target, text in backticks, otherwise the words before an opening bracket (`（(「【[`), each with a Korean particle, CJK or full-width punctuation tail after the path and a line number (`:12`, `:3-9`, `#L4`) taken off; a word counts as a path when it has a separator, an extension, is a dot file or a common bare name such as `Makefile` (`i.e` and `v1.2` don't). A build or write card that finished and wrote paths there is checked: if none of those paths changed, the progress log gets a `proof` line, the card gets `proof: { files, at }`, the report lists it under what was not checked, and the criteria check gets a line written by the code under that card ("the files this card says it changed didn't actually change"). The card is not failed or run again. Not judged: no paths written ("none"), an item that couldn't be read as a path, a closing line without the "For the next card" head (the list may have been cut), more than 8 paths, a path outside the work folder, and a changed path that lies in another card's `files` of the same step but not in this card's (who changed it can't be told). The warning is given only when every item was read as a path and none of them changed. A renamed or copied file counts its old path as changed too (in `git status` and, with `--no-renames`, in commits made in between). A file git ignores counts as changed when its modification time, read for the path as written (case kept), is inside the step. Not a git repository: nothing happens. The files' modification times are read without blocking, 16 at a time. Each git call stops after 3 seconds; when one does, when git's output is over 8 MB, or when reading the modification times takes over 3 seconds, the check is off for the rest of that run, with one log line that says which. Continuing a goal cut in a card step takes the state before the step when it continues, also when it continues at a wait, so the cards that run after continuing are checked.
- **Estimate after the plan** (`planEstimate`, `#planCheck`): once the plan exists, the remaining calls are estimated again with the same `sumEstimate` the goal card uses (the card steps as stages, the check, the returns left × (last card step + check)), shown on the plan card (`estimate: { min, max, returns, used, cap }`). If the top of that range is more than the calls left under the cap, the run asks the call-cap question of 0015 before the first card step (`hold: { reason: 'cap', kind: 'plan', min, max, used, cap, step }`; "20 more" or stop). A goal cut while this question waits keeps `at.wait = { reason: 'cap', kind: 'plan' }` and asks it again, with no AI call, when continued.
- **Report into project memory** (decided here; the repository owner's rule is that only the code-made report goes into memory, not meeting conclusions or research notes): the card has **Add to memory**; nothing goes in until the user presses it. Considered: adding it automatically when the goal ends. Chosen: only when the user presses the button, decided by the maintainer (2026-11-26). Then `reportText` (the facts and the per-criterion results, agents' evidence marked, at most 6,000 characters, never the meeting excerpts) goes into the memory of the folder the goal ran in (`memFolder`, recorded when the report is made: `m.cwd`, or the no-folder memory when that was the session's own workspace, the same rule as the session's memory), even when the session's folder changed since, with role `report`, the report's message id, its time, and a head line naming the source (report, the goal id, the time) and "a record the user hasn't confirmed". **Remove** hides it from search (`memory/<key>/hidden.json`, message ids; the text stays on disk as everything in memory does), and adding again unhides the same pieces. When the goal's AIs were models on this PC (an answer from `local`, or the request marked local), it is stored as provider `local`, so cloud AIs never get it (0007); the session title follows 0007 too. Pressing Add in two places at once adds the pieces once (the mark is set before waiting; the later press becomes "add again"), and a memory folder that two requests open at the same time is opened once (a second, overlapping open could overwrite where the next piece goes). The memory page and the session's memory badge say how many reports were taken out of search ("includes n reports taken out of search"); the piece and character counts still include them. A `hidden.json` that isn't a JSON list is not overwritten: it is moved to `hidden.json.bad` (a time-stamped name when that exists), the list starts empty, and the memory page and the answer of the next add or remove say so (reports taken out before can show up in search again); the list is written through a temporary file and a rename. The reviewer's evidence in the report goes into memory only this way, marked (0015's revision). Memory off: the button is not offered and the endpoint answers 409. Chosen over adding it automatically because an automatic insert would put agent-written evidence into later runs without anyone having read the report, which is what the draft-and-accept rule of 0013 avoids; and it keeps the decision reversible.
- **Prompt size**: `test/prompt-size.test.js` measures goal mode's fixed instruction text from what the code actually assembles, item by item in Korean and English, and fails when an item is above its value in `test/prompt-baseline.json` + 10%, telling to raise that item when the growth is meant (and naming items that shrank). The exported pieces and prompts (the blocked exit, the ask-first lines, the continuing sentence, the closing-lines rule, the assumption line, the block examples, and the plan, check, research questions, research, scan and task-card prompts) are called with empty input. What only the orchestrator assembles (the goal draft prompt, the confirmed-goal head, and the meeting's opinion, verdict, turn and conclusion prompts) is taken from the prompts a fake CLI received in a real run, with the goal's values and the marked text (what participants said) left out; English is measured by switching the app's language after confirming in Korean, since the fake CLI only recognizes Korean. The "[Continuing]" line only appears after a cut, so it is measured from the dictionary after checking that the server code still uses that exact text. This change adds no fixed prompt text; the proof line in the check appears only for a card that has a warning.

This adds `kind: 'report'` messages (with `answerFails` and `memFolder`), `mission.meetings`, `mission.reportMsgId`, `by: 'user'` on progress-log lines, the log kind `proof`, `proof` on task cards, `estimate` on plan cards, the hold kind `plan` (reason `cap`) and the same `kind` on the cut point's cap wait, role `report`, `hidden.json` and `hidden.json.bad` in project memory. Older versions don't know them: they draw a report card as "Hire proposal cancelled", ignore the new fields and `by`, read the cap wait without its kind (so a continued goal goes straight to the card step's own cap check) and find hidden report pieces in memory search.

## Consequences

- A finished goal has one place that says what happened, from records the user can follow back to the log and the messages.
- Not covered: the user's choices at an approval gate or an error wait, and instructions sent to one agent from its panel, are not in the progress log, so the report doesn't list them. When the log was trimmed (200 lines), older choices and failures are missing and the report says how many lines were left out. Answers are counted from the session's run records; a trimmed run (30 runs) drops its answers.
- Not covered: in a goal continued after a cut in a card step, the cards that finished before the cut are not checked (the state before that step isn't saved); the cards that run after continuing are.
- Not covered: what happens when git doesn't answer within 3 seconds is not tested (no way to make git slow in a test); the output-too-large and slow-file-time cases are, with a temporary git repository.
- Not covered: the changed-files check can't see a card that changed a file git ignores without touching its modification time, a file another card in the same step changed back, or anything when the folder isn't a git repository. A card that writes "none" is never checked. Whether a claimed change is the right change is the criteria check's job.
- Not covered: the report is not written for goals before this version, and the "Remove" of a memory piece only hides it from search; nothing in memory is deleted.
- Not covered: the lines taken from the progress log (what you confirmed or chose) and the agents' text stay in the language they were written in; switching the app's language doesn't translate them.
- The changed-files check adds up to seven git calls per card step (three before, three after, one more when a commit was made in between) with build or write cards (each stopped after 3 seconds); a step without such cards, or a folder that isn't a git repository, adds none that matter.
- Checked with fake CLIs in the tests (`test/goal-report.test.js`: a temporary git repository for the changed-files check, a frozen data folder for the cut). Screens checked in a real browser (fake Claude CLI, a temporary data folder, not port 4317): the report card after a goal passed (collapsed line, opening and closing it, the sections, the warning for a card whose file didn't change and the git file list in a git work folder), after accepting and after stopping at the verdict question (the chip matches the flow stage's end flag), the plan card's estimate line and the cap question asked after the plan (with "20 more"), adding to memory, removing and adding again (the memory page shows the piece as "Goal report"), English, and a phone-width window. After the review fixes (Korean, a temporary data folder): a goal accepted at a usage-limit wait of the check (the collapsed body is in the page and hidden, the button points to it, opening it shows the answers with "including 1 that ended in an error or a stop", the user's choices without the "who reviews" note, and "outside failure 1"), and the memory page and the session's memory badge with "includes 1 report taken out of search" and the warning for a broken list file. Not looked at: Simplified Chinese and Japanese (the translation test only), a dark theme, the meeting excerpt section on screen (tests only), and a goal continued after a cut (tests only).
- To undo: drop `#report` from `#missionEnd`, the `#proofSnap`/`#proofCheck` calls in `#missionWork` and `#planCheck` in `#missionRun`; the stored fields are then unused.
