# Changelog

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Goal mode, cross-review (decision 0032, which also replaces decision 0015 and rewrites the whole criteria check as it works now): the goal card's review part has a **Cross-review** switch, off by default ("+1 call per check"); the team editor's **Cross-review by default** makes it start on for that team. With it on, a second team member checks every criterion as a red team (looking for cases that break a criterion, things left out and claims without evidence): someone who isn't the lead or the first reviewer and whose AI is signed in, preferably someone who doesn't do the work (a review role) and then someone on another company's AI; the card names them, says when both are on the same company's AI and when the second reviewer is also in one of the team's work stages (it may check its own work), and says why the switch is locked when nobody fits (no reviewer, nobody else, or not signed in). Both reviewers run at the same time, each once in a new conversation, read-only for that call whatever their saved permission, with prompts built separately so neither sees the other's text; they write the same verdict block. The code merges the two per criterion: both passed = passed; a fail with evidence in a checkable form (a file path or `file:line`, Unicode names included, an `http(s)://` address, a command in backticks of three characters or more with a space, path sign, bracket or dot, a quote of twelve characters or more, an exit code; a backtick span or quote holding only criterion ids and verdict words doesn't count) = failed; the code checks only that form, not whether the file or output is real; a fail without it = split; anything else = not checked; a criterion one of them left out, or a reviewer whose block or call failed, takes the other's verdict marked "one reviewer only" with a line in the progress tab. When something is split, a **judgment card** shows each criterion's two verdicts and evidence side by side (written by agents) and you pick, per split criterion, **Fail it: have it fixed**, **Pass it: close it** or **Hold** (left out of this round's return and listed in the report), with an optional one-line reason; the card says what kind of split each one is (one passed, both failed without checkable evidence, or the other couldn't check), and your reason reaches the returned stage as your words, apart from the reviewers' marked text, only for a criterion you fail (the card says so). The progress tab logs what you picked and, on a separate line, the reasons you wrote; an export without answer text leaves the reasons out like extra instructions. When the only criteria left are ones you held, the question after the check offers accept or stop, not "once more" (nothing would be sent back); goals without cross-review keep the old question. Then the goal goes on as before (automatic return, once more, accept, no progress). Nothing is picked in advance, the card takes no other button, a repeated or stale confirm is ignored, and a goal cut while the card waits shows the same card again on **Continue** without an AI call. If, at a round, the second reviewer was deleted, left the team, is the first reviewer, isn't signed in, its AI is full or over the subscription cap, or fewer than 4 calls are left before the call cap (both reviewers asked once more for the format), that round is checked by one reviewer without asking, still read-only, with a line saying why; a goal cut and continued after the second reviewer was deleted continues this way instead of refusing. Stopping at the judgment card or discarding a goal cut there clears the card, so the flow map and the export don't show it as waiting. A verdict that came only after the format retry no longer counts as a hole. The call estimate on the card grows by one per check (and per check after a return) when the switch is on. The progress tab shows each reviewer's counts and the merged result; the goal report has a **Cross-review** part (two reviewers, rounds, split criteria, what you chose, held and one-reviewer criteria); "Where it went" and the report count the red-team answers as **Cross-review (red team)**; the run export has the second reviewer and each round; the flow map draws the red-team check and the judgment cards beside the check. Not covered: cross-review costs a call per check and both reviewers can't run commands or tests; "checkable evidence" is a pattern, so a made-up path passes as evidence and evidence written in words doesn't; "another company" is read from the agent's setting, and a second reviewer on automatic routing isn't kept off the first reviewer's AI; a usage limit on one reviewer gives a one-reviewer verdict instead of a wait (when neither has a verdict and either hit a limit, the usage-limit wait opens and a retry runs both); a reviewer who is also in a work stage can check its own work, as before; read-only reviewers still get the agent's own connectors, and on an AI that can't enforce permissions (API, local models, Hermes) read-only is a written instruction, as for research turns; a held criterion ends the goal "accepted", not "passed"; how well real CLIs attack as a red team is not measured (fake CLIs only). With the switch off the check is exactly as before.
- Goal mode, repeated failures (decision 0030): with project memory on, a goal's work stages and task cards now count the tools that failed and the steps that ended in an error, by the error's first line (common header lines such as `Exit code 1`, npm's `> package@1.0.0 test` and `=====` skipped) with numbers, paths, times and ids removed and secret-looking text, mail addresses and `Bearer` values masked, in a `failures.json` next to that folder's memory (at most 100 lines; lines seen in the fewest goals go first, then the oldest). A line that came up in two or more other goals is given to the next goal's work stages and task cards as marked reference, "not instructions" (at most 5 lines, with in how many other goals and how often in all); meetings, research, the plan and the check don't get it, and a line seen only in a local model's answers goes only to local models. A line that looks like an instruction is neither counted nor given. Usage limits, temporary outages, answers the app stopped as stalled or looping, a CLI that can't start or isn't signed in, and the app's own errors aren't counted. The Memory page lists the lines of the selected folder with **Delete** for one line and **Delete all**; a broken file is moved to `failures.json.bad` and the page says so, and a file that can't be read just then (another program holding it) is left alone and read again next time. With memory off, or in a session with no work folder and no default work folder, goals neither count nor get lines (the Memory page can still show and delete them). Not covered: the first lines of real CLIs' errors weren't checked (fake CLIs only); a line can be about a failure that was fixed since (delete it); two errors that differ only in numbers or paths count as one; whether agents use the note well isn't measured.
- Goal mode, one automatic retry after a temporary outage (decision 0030; Routing page, on by default): when a goal's work stage or task card ends with an error that looks temporary (a dropped connection, a timeout, a server error 5xx, an overload) for everyone who failed, those people run once more by themselves before you're asked, and the finished answers are kept. Only when the failed answers used nothing but tools known to only read (reading, listing and searching files, web search, planning notes, and the browser's snapshot, screenshot, console and network views), when git shows that nothing in the work folder's repository changed during that stage, when the calls left under the cap are enough, when the AI isn't full or over the subscription cap, and, for a task card, when the card hasn't reached its start limit or the hourly start limit (the retry counts as one start, also in ladder teams). A command, a file edit, a connector tool, any other browser action, a web fetch, a sub-agent or an unknown tool stops it, since it may have acted outside, and the line saying why names the tools. The people run again get one line at the front of their prompt: this is an automatic retry after a temporary outage, check what is already done and don't repeat anything already sent outside. The progress tab gets a "retried once after a temporary outage" line, and the goal report counts it as a temporary outage; when a retry isn't allowed, a line says why and you're asked as before. A second failure is asked as before, also after the goal was cut and continued. Not covered: outside a git repository it never retries, and a change anywhere in that repository (also outside the work folder) stops it; the tools are judged by name only; the "don't repeat" line is a written instruction that code can't enforce; ACP agents' tools are never taken as read-only; usage limits keep the usage-limit wait; the outage wording and tool names of the real CLIs weren't checked (fake CLIs only); research, meetings, the plan and the check aren't retried this way.
- Goal mode, export a run (decision 0030): the goal report card and the confirmed goal card have **Export run record** with an **Include text** box. It downloads one JSON file (format `office-crew-goal-run`, version 1) with the goal and criteria, the cards and their state, the progress log, meeting conclusions and your decisions, every call (who, which AI and model, kind, start and end, usage, routing, and for an error its kind and first line) and the report's facts. API keys, the notification address, the app token and other secret values from Settings are masked wherever they appear, along with token-looking text, mail addresses, `Bearer` values and the value in `NAME_KEY=…`, `NAME_TOKEN=…` or `NAME_SECRET=…`; absolute paths become relative to the work folder (the data folder becomes `<data>` and your home `~`), also when written with forward slashes, mixed slashes, another drive-letter case, or in Git Bash (`/c/…`) or WSL (`/mnt/c/…`) form, and only as a whole path (a folder `D:\work\app2` isn't cut by a work folder `D:\work\app`). Answers, the request text, the session title and the text of your extra instructions are in only with **Include text** (without it, an extra instruction's line keeps only its time and kind); the file is `goal-run-<id>.json`, or `goal-run-<id>-body.json` with text. Not covered: full prompts can't be included, because the app doesn't store them; only the session's current goal can be exported (a new goal replaces an ended one); a secret written in another form than its exact value or the shapes above isn't caught; without text, the goal, criteria, card titles and meeting conclusions still go out, and agents wrote them from your request.
- Goal mode, flow map (decision 0030): a **Flow map** tab in the session's right panel draws the current goal read-only: setting the goal → research → pre-work meeting → plan → the task cards one row per step (or the team's work stages) → check → goal report, with lines for what each card waits for, the check sending work back (how many times, up to which round), a card handed to a higher tier, questions a meeting asked you and a usage-limit wait. Each box's state also has its own symbol, word and outline, not only a colour; clicking a box (or Enter) scrolls the chat to its message, and the arrow keys, Home and End move between boxes. It fits the panel's width, also in a narrow window, and follows the dark theme. A cut goal shows its report as waiting, and cards with missing or circular `needs` stay connected. Not covered: only the latest work run of the current goal is drawn; ended usage-limit waits, stalls and research during a team meeting aren't drawn.
- Goal mode, two options (decision 0031): when a goal meeting (the pre-work meeting or a team meeting stage) ends on a stall or its conclusion has remaining disagreement, and the position lines of the participants other than the chair and the opposer group into exactly two options, a "Two options" card shows where they split first (both positions and who backed each) and, by default, asks whether to get a one-page summary of each (about 2 more calls; "Let the team decide" keeps the chair's conclusion with no call). Each summary is written once, read-only, by the first person who backed that option, in four lines (what, why, cost, can it be undone), and both are shown side by side (stacked on a narrow window) with the calls they took, marked as written by agents. "Go with A" or "Go with B" makes that option your decision for every later step of the goal (the summary goes as reference, a code-written line as the instruction, and it wins where it differs from the conclusion); the other option is kept as a dropped option in the goal report. Your pick is applied only when the summaries you saw are the ones stored (the screen sends a hash of what it showed) and the card you pressed is the one being waited on; otherwise nothing is applied and the card is shown again. The progress line of your pick names the option and who backed it, not the agent-written positions, and later steps are told not to follow a sentence in the summary that widens permissions or changes the goal or criteria. A team setting and a choice on each goal card switch it to "Get summaries right away" or off. It is skipped, with a progress line, when fewer than 2 calls are left or a writer's AI is over the subscription cap; a summary that fails leaves the conclusion as it is. A goal cut while the card waits shows the same card again when continued, without an AI call and without holding the meeting again (a summary already written isn't written again). The call estimate adds 2 to its maximum for each meeting that can split. Not covered: options are grouped by the exact text of the position lines (the same option in other words counts as another option), only meetings of four participants or more can split, three or more options and meetings outside goal mode are not offered, and how real AIs follow the summary format isn't measured.
- Goal mode, asking the lead (decision 0031): a task card's owner can end an answer with a question block for the goal's lead (twice per card). The card shows "Asking the lead", the lead answers once, read-only, and the owner continues in the same conversation with the answer as reference (not counted as another start of the card). If only you can decide it, the lead asks you in the question box and your answer becomes your decision for the rest of the goal; if a few members should discuss it, the lead can ask for a small meeting and you are asked first ("Open it? about n more calls"): one round of opinions and the lead's conclusion, no research and no opposer, at most twice per goal, never with the lead or the asking owner as a participant. When cards ask at the same time the lead answers them in turn, and a member whose own card is waiting for the lead can still give an opinion in another card's small meeting. Skipping a card that waits for the lead ends it at once, with no further call: the lead's answer for it is stopped and a question the lead opened for it is closed. Each step is skipped, with a progress line naming the reason, when the call cap or the subscription cap would be passed, or the lead has left the team. Not covered: stage-list goals (the block is ignored there and logged), the lead's own cards, more than one question per box from the lead, keeping an open lead question across a cut (the card restarts and the count stays), the call estimate doesn't include these calls, and the checks before them count one call per run (a retry inside that run can use one or two more).
- Goal mode, ladder teams (decision 0027): a team can be a ladder team (a team made from a document is one; any team can be switched on in the team editor with "Ask after this many failures", 1 to 5, default 2) and each agent can have a tier from 1 to 4 in the agent editor: a difficulty grade across the whole team (1 simple chores … 4 the hardest work), and several AIs can share a grade. In a ladder team a task card that has started that many times (error retries, "once more" after a block and returns count; a retry after a usage limit doesn't) stops before its next start and asks as before, with up to two more choices: "Hand to a higher tier — name (AI · model · effort)" for the next grade up in the team, one member on the owner's AI first and one on another AI when the grade has both. Members whose AI isn't signed in are left out (the question doesn't skip to a grade above for that). The answer names the member; if that member stopped being a candidate meanwhile (team, agent or sign-in changed), nothing moves and the question is asked again with fresh choices. Nothing moves up by itself. The new owner works on the card in a conversation of its own for that card, with the previous owner's last answer (first 1,500 characters) and its blocked reason as reference inside markers; the new owner's own conversation is kept, and after the goal its next message continues that conversation and gets the card's answers as missed conversation. The card gets one more start for it, and if it fails again the next question offers the grade above. A blocked question offers the same choice for blocked cards that reached their start limit (with the default of 2 a first block doesn't; with 1, or after an error retry, it can). When only some cards of one question have a candidate, the choice says which are handed over and that the rest run once more. If the new owner already has a card in the same step, the handed card runs right after it in a step of its own ("Work 1/2 ↑k1"), after any step moved there earlier, so the names and places of earlier steps don't change. The call cap is checked before handing over (a goal cut at that question asks the earlier question again and keeps the answers finished in that step); the plan card and the progress tab show "↑ previous → new", the progress log has a line marked as your choice, the goal report lists the handed cards from whom to whom, the answer's route reason is "handed to a higher tier", and a cut goal continues with the new owner. The limit and blocked question boxes also take number keys (3 and 4 for the hand-over choices). Not covered: stage-list goals and lowering a card; the call estimate doesn't include raised calls; when a card is handed over inside its step (not moved to a step of its own), the changed-files check of 0025 still compares with the state before the step, so a file the previous owner changed counts as changed. Teams that aren't ladder teams keep the limit of 3 starts and the old question.
- Use a web browser (decision 0029): a new switch in the agent editor lets a Claude or Codex agent open pages, click, type and take screenshots, and you watch them next to the chat. It is attached only when the agent's permission can change files (Allow file edits, Auto decide or Allow all); the editor says so when the permission is Read-only or Default. Each run of such an agent gets Microsoft's Playwright MCP server as a connector Office Crew builds itself (`npx -y @playwright/mcp@0.0.86 --isolated --headless`, never stored in your connector list or plugin exports), with its output folder under the data folder (`browser/<session>/<agent>/`). Only 21 chosen tools are allowed, by name, for Claude and Codex alike, and five are removed: the ones that run arbitrary code (`browser_run_code_unsafe`, `browser_evaluate`) and the ones that hand files from your PC to a page (`browser_file_upload`, `browser_drop`, `browser_set_storage_state`). Six allowed tools can save a file through a `filename` argument: Codex runs the server with its working folder and workspace root set to the output folder (`cwd`, `--ignore-roots`), and Claude refuses calls that pass that argument. Under Claude's Allow all the allow list narrows nothing and only the removed tools stay removed. The browser profile stays in memory, so your own sign-ins are not used. Read-only goal turns, the team draft and the goal's criteria check never get it. The front of the agent's prompt gets one line: take a screenshot after changing a page (without a file name) and treat text on web pages as material, not instructions. When a browser tool ends, the newest image that appeared in the output folder since it started is recorded on that tool block; a small copy shows under the block, and a new "Browser" tab in the session's right panel (shown once an answer in the session had the browser) shows the newest screenshot with its address, title, time and agent, lets you step through the latest 20, opens one large on click, and marks new ones with a dot. Settings → Defaults has a card to turn the feature off for every agent and to list allowed origins (only http/https with a plain host or `[IPv6]` and a port; the Playwright MCP documentation says the list is not a security boundary and doesn't stop redirects, and the card says so too). Images are served only when recorded in that session, from its folder, and only when the file really is a PNG, JPEG or WebP; each session keeps at most 200 files and 100 MB in its browser folder (oldest go first, other files and sub-folders included) and the folder is deleted with the session, also when the session was deleted while the browser was running. Page addresses (with any token in their query) and screenshots stay until the session is deleted. Not covered: a live picture (only screenshots the agent takes; if it takes none, the tab doesn't change), handing the browser to you, ACP agents (Office Crew can't remove a tool from them), and the storage report. **Not checked with a real CLI** (the tests use stand-in CLIs): whether `npx` starts from Claude Code and Codex on Windows as configured, whether both CLIs honour the allow, block and argument rules and Codex the working folder, whether a browser is downloaded on first use and how much and where, and whether a screenshot really lands in the output folder under a name the app accepts. The decision record ends with a short manual check.
- Meetings notice a stall (decision 0028): in a three-round meeting with at least two people taking turns besides the chair and the opposer (four participants or more), when after round 2 those people each keep the position line of the round before, the code skips the chair's verdict and the chair concludes at once, told to decide from what has been said and write down the remaining disagreement. A new meeting stage has two rounds, so with the default settings a meeting never stalls; set three rounds to use it. A round in which research during the meeting brought back an answer is not a stall (the chair sees the result in its verdict). The round cap, the usage cap and "End meeting" still come first. The conclusion shows "Concluded on a stall", the flow stage's meeting station "Stalled", and a goal's progress tab gets a line. A switch in the team's meeting settings turns it off (on by default); next to it the editor says when it works and dims it for a meeting that doesn't qualify. The pre-work meeting of a goal (two rounds) never stalls, and whether real AIs keep writing the position line is not measured.
- A meeting can ask you (decision 0028): when something only you can decide blocks a meeting, the chair can ask one question with 2 to 4 choices, either in its verdict between rounds or instead of its conclusion; it opens in the same question box as an agent's question (numbered choices, your own answer, skip) and the meeting waits. Your answer, with the chosen option's description as reference, is kept as your decision and goes, as an instruction, into the rest of the meeting and the later stages (in a goal: work stages, task cards, the plan and the criteria check); the goal report lists it under what you chose. Skipping tells the meeting to decide and write down its assumption. A question asked instead of the conclusion is followed by the chair writing the conclusion once more with your answer (one extra call, only when you got a question; once per meeting). Where it can happen: any meeting can ask at its conclusion; from a verdict, an ordinary meeting asks only with three rounds (after round 2), and a goal meeting also after round 1 (two rounds with three or more participants, or three rounds). At most 2 questions per meeting, retries included, and only where agents may ask (not in scheduled runs or with asking turned off); otherwise the chair's question is read as "continue" and the message says so with the question. A goal cut while the question waits asks it again, without an AI call, when you continue it ("End meeting" isn't offered then, since nothing has been said yet). A skipped question is not kept after a cut.
- Goal mode, no progress (decision 0028): when a criteria check fails the same criteria with the same evidence as the check before (also after "once more"), the verdict box says "Another try failed the same criteria for the same reason", the progress tab gets a line and the goal report counts it under what was not checked. The goal already asked you instead of returning the work again after the second check (one automatic return); the code now also refuses an automatic return in this case, which only matters if more automatic returns are allowed.
- Team from a document (decision 0024): attach a text document (`.md`, `.markdown` or `.txt`, up to 200 KB, the first three are read) and send a short request that ends by asking to make a team, such as "set up a team from this doc" (word rules in Korean, English, Chinese and Japanese, no AI; "make a team intro page from this doc" or "팀장님께 보낼 메일 만들어줘" stay ordinary messages). Instead of an ordinary run, the session team's lead (else the session's agent, else the default agent) reads the documents once, in a new conversation without memory, role notes or the attached pictures. The call gets the read-only permission mode, which holds as far as the AI's CLI enforces it; an AI whose CLI has tools but no permission control in the app (Hermes) is never chosen to write the draft, and the call doesn't run if automatic routing picks one. An AI that isn't signed in is skipped too. A team proposal card appears: the team name, each agent's role, AI, model and effort, the document's own wording, warnings, and the stages. The code checks the draft: only AIs signed in now and models in their lists (otherwise automatic routing or the closest model by tier, with a warning), efforts the model accepts, at most 8 agents and 8 stages, names that differ only in spaces, case or full-width forms numbered apart, lengths cut the way Create cuts them; a team or stage name that looks like an instruction is replaced with a neutral one and shown as a warning; permissions, instructions and tools written in the document or by the AI are ignored. You pick the permissions (for everyone and per agent, default "Default"; "Allow all" and "Auto" show a warning) and press Create to make the agents and the team, and the session switches to it unless you untick that. "Just send it" runs the message as an ordinary request. If you stop the draft or the app closes during it, the message becomes an ordinary message and a line says so; if the writer's run fails, the line says the run failed. Agents get a tier (1 to 4) and the team is marked as a ladder for a later step that asks before handing a task to a higher tier; nothing uses them yet. Not covered: tables in pictures or PDFs, a button on the Teams page, editing the draft on the card; real CLIs following the block format is not measured. A text document attached to a message already went to the agents as a file path; uploads were not changed.
- Goal mode, report and evidence (decision 0025): when a goal ends (passed, accepted or stopped), a "Goal report" card appears in the chat, put together by the code with no AI call. Collapsed it is one line (end state, time from confirming to the end, actual calls next to the estimate, criteria passed); opened it shows answers by kind (goal, research, meeting, plan, task cards, work stages, check; answers that ended in an error or a stop are counted and their number shown), each criterion's final verdict with the reviewer's evidence marked as written by an agent, what you chose along the way (from the progress-log lines that record your choices, not the code's own notes), what was not checked (unknown criteria, research questions without an answer, cards left as gaps, blocked or skipped, cards whose changed files didn't change, skipped stages, usage-limit stops), the failure kinds (one usage-limit event counted once), how many answers were routed differently, the uncommitted files git reports, and the decision and remaining disagreement of each goal meeting. A goal cut by closing the app gets its report when it is continued and ends, once. Meeting conclusions in a goal are read into decision, reasons, remaining disagreement, dropped options and next steps (from the format the conclusion already asks for; a conclusion without it is kept as it is and nothing is made up); the next steps still get the whole conclusion. In a git work folder, a build or write task card whose "Changed files" line names files that didn't change gets a warning in the progress log, in the report and as one line in the criteria check's material; the card is not failed. The paths are read past Korean particles, CJK text, brackets, links, backticks and line numbers, renames count the old name too, and a card is not judged at all when any item of its list can't be read as a path. After the plan, the remaining calls are estimated again (shown on the plan card), and if the top of that range is over what is left under the cap, the run asks "20 more?" before the first card step. The report's card has **Add to memory**: only then does it go into project memory, the memory of the folder the goal ran in (the facts and per-criterion results, marked as a code-made record you haven't confirmed; not the meeting conclusions or research notes), and **Remove from memory** hides it from search again; the memory page and badge say how many reports are hidden that way. Not covered: choices at an approval or error wait and instructions sent straight to an agent are not in the progress log, so the report doesn't list them; the changed-files check can't see files outside the work folder or anything when the folder isn't a git repository; reports aren't made for goals that ended before this version.
- Usage you can read and guard (decision 0026). Single token numbers are now **weighted**: new input + cache writes + output + cache reads ÷ 10, the count the meeting usage limit already used, from one function the server and the screen share. Before, the four were added 1:1, so a run that mostly read the cache looked far bigger than it was. Where a total appears (the bottom-right indicator, the Usage page, the session's Usage & limits tab, under each message, the run bar, the team cards) it is labelled "weighted", and the four parts and the 1:1 sum are shown or in the tooltip; the office name tags still show the 1:1 sum. The Usage page shows each AI's four parts and each agent's cache hit rate (cache reads ÷ (new input + cache reads + cache writes), only for agents that reported cache numbers). The session's Usage & limits tab has a new "Where it went" card: weighted usage by kind and by agent with cache hit rate, optionally only for the session's goal, and a "Show the parts" switch that writes each row's four parts out (keyboard and screen readers get them too). The kinds come from one function the goal report also uses (ordinary run, set the goal, research including research during a meeting, meeting, plan, work stage including returns, task cards, review, team draft, handoff note), read from marks the messages carry; answers in a goal now carry the goal's id, so a goal's work stages no longer count as ordinary runs and "This goal only" keeps answers whose run record was dropped (estimates for answers still being written are not counted there). Claude's "used outside the main agent" line is weighted too. The agent editor shows the fixed text sent with every new conversation (name, role, instructions, role notes and skill bodies, counted by the server from the values being edited; characters, not tokens) and a warning when skill bodies are 10,000 characters or more. **Subscription cap** (on by default at 90%, set on the Routing page; 0 turns it off): before a goal starts new work (research, a meeting, the plan, a stage, a card or the criteria check), if a known limit window of the AI that would do it is at or above the cap, it asks instead of starting: continue (and don't ask again about that AI in this goal), continue after the reset (only when the reset time is known; the same timer and the same three-per-goal count as the usage-limit wait) or stop. Moving the work to another AI near a limit (or over its daily budget) and waiting for a reset that is due soon still come first, and an automatically routed agent is checked on the AI it would get; AIs that report no percentage aren't checked; an AI whose window is already full (100% or a rejection record) isn't asked about, since the usage-limit wait handles it; a meeting also checks its research agent; an AI already asked about in a usage-limit wait isn't asked again; a goal cut at this question asks it again without an AI call when continued, and answers the stage had already finished are kept (also at the call-cap question). A task card's retry for its two closing lines isn't checked. The goal card's limit line shows the cap and marks only the AIs the cap would ask about now (counted by the server the same way), and the flow stage puts the gate before the stage (inside it when the stage already ran). With project memory on, your own message is now stored when its run ends (or when the app closes or restarts during the run) instead of when you send it. ### Added

A public ntfy topic can be read by anyone who knows its name, so pick a hard one to guess.

Added ChatGPT accounts and Codex sessions started more than two days ago aren't watched.

Once a quarter of the share is used and today is going faster than the day, a run's effort is lowered one or two steps (never raised, never below low; the saved agent doesn't change). An AI that used its share hands off to another AI until midnight; with no other AI available, or with auto-handoff turned off, work continues at low effort. A review keeps its cross-check first: it may still use an AI that's over budget, at low effort, rather than the AI that built the result. An AI taking over after a usage limit follows the same pace. Today's spend counts from the first weekly reading the app sees today (usage while the app was closed isn't counted), and only AIs that report weekly usage are affected. "Use again" on an AI that's over its share lifts it for the rest of the day. A scheduled run is stricter: if no AI within budget can take it, that time is skipped instead of running at low effort ("Run now" still runs).

Hermes isn't watched, because it gives its whole result at the end.

A conversation with a local model isn't passed to a cloud AI this way, or when recent conversation is added to a new or handed-over run.
- Leftover CLI cleanup: running CLIs are recorded in `running-cli` in the data folder. If the app was killed or the power went out, the next start stops CLIs it left behind, only when both the start time and the name match (so a reused process ID never stops another program), and leaves the record of another running copy of the app alone.
- Schedules: on the days and at the time you pick, a team (or a single agent) gets the same instruction and starts working on its own, in a new session each time or continuing one session. Times use this PC's clock and only run while the app is open. A time missed while the app was closed is skipped by default, or run once when the app opens if you turn that on. If the previous run hasn't finished, that time is skipped. Approval steps wait for you as usual. Run now, turn on or off, and the last result are on each card.

## [1.1.0] - 2026-11-03

### Added
- Needs you: the top of the sidebar collects sessions that need you (approvals, decisions after an error, paused runs, failures and results you haven't opened yet). Results and failures leave the list once you open them; approvals, decisions and paused runs stay until they're handled.

A review done by the same AI that built the result, including one that took the review over after a usage limit, is flagged as weaker than a cross-check. - Claude Code, Codex, Gemini CLI and Hermes now rest until the reset time stated in the limit error when their usage data has no full window, instead of a flat 30 minutes. Recognized forms: `Retry-After`, "try again in …", "try again at …", "resets 3pm" and an epoch suffix; a time zone after the time (UTC, an offset such as UTC+9, or a name such as `(America/Los_Angeles)`) is honored. A time that passed less than two hours ago falls back to 30 minutes, and waits shorter than a minute become a minute.
- Auto-routed review agents avoid the AIs that built the result (every earlier build stage, or the previous stage when there was no build). Before, only the nearest stage with output was avoided.
- Environment variables and headers of connectors, and environment variables of ACP agents: names that contain `AUTH` or `COOKIE` but end in a setting word, such as `LOGIN`, `LABEL`, `GUARD`, `MODEL`, `PKCE` or `ONLY`, are shown as normal values instead of being masked.

Other paths outside the work folder are still refused before the file system is touched, except on Windows when the path or the work folder contains `~` (a possible short name) and the path is on the same drive; those are resolved first and then refused if they really are outside.

## [1.0.0] - 2026-11-02

First public release.

### Added

#### Providers
- Runs your own installed and signed-in official CLIs: Claude Code, OpenAI Codex CLI, Gemini CLI (API key) and Nous Hermes Agent.
- Billing per AI for Claude Code and Codex: subscription sign-in or an official API key (`ANTHROPIC_API_KEY` / `CODEX_API_KEY`). Subscription mode strips those variables from the CLI environment so a stray key never bills you by surprise.
- ACP (Agent Client Protocol) agents: presets for Gemini CLI `--acp`, Hermes `acp`, OpenCode, Goose and Qwen Code, or any custom ACP command. Permission requests follow the agent's permission level; file reads and writes the agent asks Office Crew to do stay inside the work folder (reads also cover attachments).
- OpenAI-compatible APIs: OpenAI, OpenRouter, Nous Portal, xAI and the Gemini API.
- Local models detected automatically: Ollama, LM Studio, llama.cpp, vLLM and Jan, plus custom server URLs.
- Built-in demo provider with zero usage, for trying the app and for tests.
- Settings → AI accounts: install status, version, signed-in account and supported effort levels per CLI, with a sign-in button that opens the CLI's login in a terminal.

#### Agents and routing
- Per-agent provider, model, effort (low to max, xhigh where supported), permission (read-only to full access), system prompt, skills, MCP connectors and avatar.
- Model dropdowns fed by each CLI's own model catalog, refreshed automatically every 30 minutes and when a CLI update is detected.
- Auto-routing, the default for new agents: picks a model and effort at run time from the AIs you're signed in to, by role (research, organize, analysis, build, review, writing) and profile (economy, balanced, best). Review is cross-checked by a different AI than the builder whenever possible.
- Routing board to edit every agent's routing in one table.
- Automatic handoff: when an AI hits its usage limit, another AI with headroom takes the same role and finishes from where it stopped. AIs that are resting or above a usage threshold (95% by default) are avoided before a run. Toggle, threshold and manual release on the Routing board.

#### Teams and runs
- Team pipelines: stages run in order, agents within a stage run in parallel, and previous outputs are handed off automatically.
- Approval gates (approve, or request changes to rerun the stage with feedback) and an error gate (retry, skip or stop).
- Live intervention: steer a running agent (injected into the running process for Claude), queue messages, pause/resume, stop, and skip a single agent.
- Real-time usage per message, agent and session: estimated tokens while streaming, real counts at turn end, cost where the CLI reports it, and account limits (Claude 5-hour and weekly %, Codex weekly %).

#### Live office
- Isometric SVG office with no game engine. Characters walk to the Research room, Library, Server Room or Meeting Room by tool type, raise a hand for approvals, sweat on errors, carry documents on handoff, and spawn sub-agent helpers.
- Skins: Modern, Cozy and Night, plus custom image skins with a desk and spot editor.
- Quality levels `full`, `lite` and `static` for low-end PCs.

#### Desktop-app experience
- Sessions with search and pinning, image paste (Ctrl+V), drag and drop, `@agent` mentions and `/skill` commands.
- Markdown with copy buttons, resend and edit, export a chat to `.md`, and dark mode.
- Skills discovered automatically from Claude and Codex skill folders, MCP connectors injected per agent, and plugins that bundle agents, teams, skills, connectors and skins into one JSON file (import/export).
- Import and continue Claude Code and Codex sessions without losing context. Claude continues on a fork (`--fork-session`) so the original history is untouched; if resuming fails, the recent conversation is passed along instead.
- UI languages: Korean, English, Simplified Chinese and Japanese.

#### Platform and security
- Zero runtime dependencies (Node.js built-ins only), no build step, UI built with vendored Preact and htm (about 16 KB).
- Launcher opens an Edge/Chrome app window, with `--browser`, `--port`, `--home` and `--no-open` options; Windows launcher script `오피스크루 실행.cmd`.
- Server bound to `127.0.0.1` with `Host`/`Origin` checks and a per-install token; agent output escaped before markdown rendering; API keys masked in the UI.
- Test suite with fake CLIs (zero AI usage) and CI on Windows, Linux and macOS with Node.js 20 and 22.

#### Documentation
- "Using your accounts" guidance in the README (four languages) and in the app: official CLIs only, no access to CLI sign-in tokens, API keys for products, teams and unattended runs.
- Google Antigravity CLI is intentionally not supported, because its personal-account terms don't allow use through third-party tools. Agents saved by pre-release builds that used it switch to auto-routing.
