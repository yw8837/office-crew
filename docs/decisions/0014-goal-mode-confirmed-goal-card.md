# 0014: Goal mode turns a request into a goal card the user confirms, and only the confirmed values become instructions

- Status: Accepted
- Date: 2026-11-19
- Related: [0006](0006-hire-proposal-in-chat.md) (a card in the chat the user approves), [0007](0007-local-only-user-messages.md) (what only a local model saw stays away from cloud AIs), [0009](0009-agents-ask-with-a-marked-block.md) (marked blocks at the end of an answer), [0013](0013-agents-keep-role-notes.md) (the injection check), `server/mission.js`, `server/orchestrator.js` (`send`, `missionProblem`, `#missionNote`, `#goalTurn`, `confirmMission`, `cancelMission`, `discardMission`, `sendProposed`, `#missionStage`, `#missionEnd`, `#goalCardPrompt`, `#prompt`, `#received`, `handoffWriter`, `#autoWriter`, `recover`, `stopAll`), `server/store.js` (`#fixStale`, `#metaOf`), `server/notes.js` (the injection patterns), `server/index.js` (session `PATCH`, `/mission/*`, `/proposals/:mid`), `server/providers/mock.js`, `public/js/views/mission.js`, `public/js/views/session.js`, `public/js/chat-tools.js` (`hideGoal`), `test/mission.test.js`

## Revision (2026-11-20)

[0015](0015-goal-mode-fresh-review.md) adds the criteria check by a fresh reviewer. A confirmed goal now ends `done` (every criterion passed), `accepted` (the user accepted what was left) or `stopped`, and is `waiting` while the run asks after a verdict or at the call cap. Review stages without an approval gate that aren't meetings are replaced by the check unless the user ticks **Keep** on the card (a confirm without `review` still skips nothing). An extra instruction sent while the work run is going no longer gets `late: true`: a run that ends with unused instructions asks whether to use them. `unreviewed` stays readable as the end state of older goals. The sentences below that said these were planned are updated.

## Context

A team runs its stage list once and stops. Nothing says what "done" means, so a run can end with "the next step needs your approval" and the user can't tell whether the request was met. Making a team carry a request all the way needs, first of all, a goal and acceptance criteria the user agreed to, a step-by-step record, and later a fresh reviewer that judges each criterion. This record covers the first part: the goal card, and running the existing stage list with the confirmed goal attached.

## Options

1. Let the lead write the goal and start at once. Cheapest, but a wrong goal wastes everything after it, and text an AI wrote (possibly copied from a web page) would become an instruction to the agents that edit files.
2. Put a goal and criteria in each team's settings. Fixed per team, not per request.
3. A goal mode per session: the lead drafts a goal card from the request, the user confirms, edits or drops it, and only the values the user confirmed go to every stage as instructions.

## Decision

Option 3.

- Session fields: `goalMode` (boolean) and `mission`: `{ version: 1, id, status, phase: 'goal'|'work', request (first 2,000 characters), requestMsgId, leadId, goal, criteria: [{ id: 'c1', text, status: 'open', evidence: '' }], outOfScope, userDecides, notes: [{ id, text, at, used, msgId, files?: [{ name, path }] }], cardMsgId, confirmedAt, editedByUser, cutNotice?: 'drafting'|'cut', log: [{ at, kind, text, msgId?, n? }], createdAt }`. A session has one goal; a new goal replaces an ended one. The log keeps 200 lines; older lines are dropped and counted in one "n earlier lines left out" line (`kind: 'skip'`, with the count in `n`). `cutNotice` is set when a session is read from disk after the app closed mid-goal and is removed once the chat line is written (or when the cut goal is discarded).
- Status: `drafting` (the lead is writing the card) → `draft` (the card waits) → `active` → an end state: `unreviewed` (all stages ended; nobody has judged the criteria yet), `stopped`, `cancelled` (the card was closed, the goal turn failed, or a cut goal was discarded). `cut` means the app closed while the goal was running. `drafting`, `draft`, `active`, `waiting` and `cut` count as alive: while one is alive no new goal is made, and goal mode can't be turned off or the team changed (409). `waiting`, `done` and `accepted` are set by the criteria check (0015).
- Turning it on: `PATCH /api/sessions/:id { goalMode }`. It is refused with 400 and the reason for a session without a team, for a team that mixes models on this PC with cloud AIs (an agent with automatic routing counts as either, so it mixes with a local-model agent; a team of only local models is allowed), and for sessions started by a schedule or a board card. The same check runs again when a request becomes a goal and when a card is confirmed. Changing the team of a goal-mode session to one that fails the check turns goal mode off.
- Which messages: in a goal-mode session, a message without an `@name`, not a handoff request and not from a schedule is looked at before "interrupt now" and before hire detection. With no alive goal it becomes a goal turn; with a waiting card that card is closed and a new goal turn starts; with a running goal it becomes an extra instruction; with a cut goal it gets 400. While the card is being drafted, such a message goes to the lead as an instruction (steer), whichever mode ("interrupt now" or "next in line") was picked; it never replaces the goal. If another run is going, the request waits in the queue (`mission: true` on the message) and starts as a goal turn when its turn comes. "Send as is" on a hire card (0006) follows the same rule in a goal-mode session: with no alive goal the message starts a goal turn, with an alive goal it gets 409 and the card stays open.
- Goal turn: a run with one stage and the lead alone. The lead is the chair of the team's first meeting stage, else the first member whose role is analysis, else the first agent of the first stage. The prompt tells it not to start the work and to write a goal (one line), 2 to 7 criteria that can be checked by opening a file or running a command, what is out of scope and what only the user can decide, ending the answer with one fenced `oc-goal` JSON block. The block is read only when it is the last thing in the answer (as in 0009). Values are cleaned: one line, control and invisible characters removed, the goal up to 200 characters, criteria up to 300 characters and 7 items, the other lists up to 5 items of 200 characters. A block with one criterion is accepted. If no block can be read, the lead is asked once more in the same run; if that fails too, the card uses the first 200 characters of the request as the goal and has no criteria, with a notice. The lead may ask the user with `oc-ask`. An error, a stop or skipping the lead closes the goal without a card; an error or a skip also leaves a line in the chat (a stop is the user's own action and only gets a log line). The lead's draft answer (`goalDraft`) is left out of what is passed to other agents and out of project memory, doesn't count as an answer when choosing who writes a handoff note, and is cut from the session list preview; the screen hides the block's span (`goalBlock`). The lead's CLI conversation state for this session (`providerSessions`, `sessionProvider`, `usageBase` and `noteHashes` for the lead) is saved and cleared when the goal turn starts, so the goal turn always begins a new conversation, and put back when it ends, done, failed or stopped, so the work stages don't continue the goal turn's conversation with the unconfirmed draft and what it read then.
- Goal card: a message `{ id, role: 'proposal', kind: 'goal', status: 'open'|'confirmed'|'cancelled', text: '', missionId, leadId, draftMsgId (the lead's answer the card was read from, null for a card made from the request), goal, criteria, outOfScope, userDecides, warn?, fallback?, createdAt, confirmed?, edited?, resolvedAt? }`, kept out of what agents get, like the hire card of 0006. The injection check of 0013 runs over the draft; a hit puts a warning on the card and does not block. The check also catches tags that imitate the one the app wraps instructions in (`<역할 지침>`, `<role instructions>`, `<角色指令>`, `<役割の指示>`, opening or closing, full-width too); role notes use the same patterns. `POST /api/sessions/:id/proposals/:mid` refuses every card whose kind is not `hire` (409).
- Confirming: `POST /api/sessions/:id/mission/confirm { missionId, expected, edited? }`. `expected` is the card the screen showed; its goal, criteria, out of scope and user-decides lists must all match the stored draft character by character, or the answer is 409 with the current draft and the screen redraws it. It is also 409 for another goal's id, a goal that is not `draft`, a run in progress, a card that is not the session's latest goal card, and a card followed by any user message. It is 400 when the goal or the criteria are empty, or the team check fails now. `edited` holds the user's values (cleaned the same way) and sets `editedByUser` when they differ. Nothing waits after the body is read, so a double click confirms once. The run is put in before the session is saved, so a running goal is never stored without its running run. An error reply carries only `error` and, for the 409 above, `draft`. `POST …/mission/cancel` closes a waiting card; `POST …/mission/discard` closes a cut goal.
- Work: one run with the team's stage list as it is: no stage is left out, review-role stages and approval gates included (meetings, approval and error gates unchanged). Criteria judging doesn't exist yet, so leaving review stages out would remove review altogether. Done in 0015: review stages without an approval gate that aren't meetings are replaced by the criteria check, and the card shows which stages will be left out (with a Keep box) before the user confirms. Each stage's own prompt begins with `[Confirmed goal and acceptance criteria (confirmed by the user. Don't change them)]`: the goal, the numbered criteria and what is out of scope, with `<` and `>` turned full-width (`＜` `＞`, as in 0013) so a value can't close or imitate a tag. What the app puts in front of a stage's prompt as before still comes first: project memory pieces, a handoff note, the conversation an agent missed since its last answer, and for an agent with no CLI conversation to continue the earlier conversation (`[Previous conversation]`). Those are the only goal values given as instructions, and the run uses the values held in memory from the moment of confirming. When all stages end, the goal is `unreviewed`, not done; a stop or an internal error makes it `stopped`.
- Extra instructions: a message sent while the goal runs is stored as a note and as a user message marked `missionNote`, is left out of the earlier conversation, the missed conversation and the whole-conversation file, and goes under `[Additional user instructions]` into every stage that starts after it, and into a stage that runs again after "reject" or "retry" when it came while that stage waited at an approval or error gate (marked `used`; `<` and `>` turned full-width as above). A goal takes up to 50 notes; the 51st gets 400 with the reason. When no stage is left to start (the last stage is already running and not waiting at a gate), the reply carries `late: true` and the screen says the note may not be used for this goal; notes that were never used are counted in the log when the goal ends. The message goes into project memory when the goal run ends, not when it is sent (also when the app is closing, and when a cut goal is read back after a restart): marked local (0007) when every AI that received it was a model on this PC, unmarked when any cloud AI received it, and judged by the team at send time when no AI received it. An instruction sent to one agent from its panel goes in directly as before and gets a log line.
- Restart: when a session is read from disk, `drafting` becomes `cancelled` and `active` or `waiting` becomes `cut`, each with one chat line at start (`cutNotice`). Nothing starts again by itself. A waiting card stays and can be confirmed. A cut goal can be continued when the user asks (0016).
- Order and models: the order (goal turn, then the stage list) is fixed in code. Each agent keeps its own model and the user's overrides; no router picks models by how hard a task looks.
- The event `mission { sessionId, goalMode, mission }` is sent on every change (the session summary event doesn't carry these fields). The demo provider recognizes the goal turn only when the prompt ends the way the code ends it (with the block example), not when a request merely contains "[Set the goal]", and answers with a block, so the flow can be tried with the demo team at no usage.

This adds `goalMode` and `mission` to sessions, `kind: 'goal'` cards, and `mission`, `missionNote`, `goalDraft`, `goalBlock` on messages and `mission`, `missionId` on runs. Older versions don't know them: they run every message as a normal request, draw an open goal card as an empty hire card ("Cancel" marks it dismissed, "Hire" and "Send as is" fail) and a closed one as "Hire proposal cancelled", and pass `goalDraft` and `missionNote` messages to agents as earlier conversation.

## Consequences

- Each goal costs one AI call before the work starts (two when the block has to be asked for again), plus any question the lead asks.
- A user message after the card, even one to `@name`, makes that card unusable; the user sends the request again. Clearing the conversation drops the goal.
- Judging each criterion with a fresh reviewer, one automatic return for fixes and a cap on calls per goal are covered by 0015. Continuing a cut goal from where it stopped is covered by [0016](0016-goal-mode-continue-a-cut-goal.md). Research, meetings planned by the lead and task cards are not part of goal mode.
- Not covered: the criteria can't be changed after confirming (drop the goal and send the request again); goal mode isn't available in scheduled runs, board cards, or teams that mix local models with cloud AIs.
- Not covered: how reliably real CLIs follow the `oc-goal` format is not measured; the tests use fake CLIs only.
- Not covered: pausing during the goal turn does nothing (a pause is only checked between stages and between meeting turns, and the goal turn is one stage). An extra instruction sent by mistake can't be taken back. Extra-instruction messages are left out of the earlier conversation passed to agents even after the goal ended. A team of cloud AIs with an automatic-routing agent is allowed although that agent can end up on a model on this PC during the run. Once the user confirms, sentences an agent wrote become instructions, so the card has to be read before confirming; the warning only catches common patterns.
- Screens checked in a real browser: `with the demo agents (no AI usage): turning the switch on by the switch and by its word, the refusal in a session without a team, the goal card and its three buttons, editing a criterion before starting, Enter alone not starting it, an extra instruction during a run and during an approval wait (used when the same stage ran again), the approval gate of a review stage still showing, the progress tab, the request bar keeping the original request, the session preview without the block, and the cut notice with Discard after the app was killed mid-run. Not looked at: the dialog that Discard opens (checked through the endpoint), the card redrawn after a 409, Stop on the card, clicking a progress line, the English, Chinese and Japanese screens, the dark theme and a narrow window`.
- To undo: drop the goal branch in `send` and the `goalMode` handling in `PATCH`; stored `mission` fields are then ignored.
