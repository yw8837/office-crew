# 0022: Goal mode keeps one table of the blocks each step takes, records who actually ran and why, and names failures only by facts the code knows

- Status: Accepted
- Date: 2026-11-25
- Related: [0014](0014-goal-mode-confirmed-goal-card.md) (goal mode), [0015](0015-goal-mode-fresh-review.md) (the criteria check and its mixed-block rule), [0016](0016-goal-mode-continue-a-cut-goal.md) (the "[Continuing]" line), [0017](0017-goal-mode-research-and-meeting-first.md) (research during a goal meeting), [0018](0018-goal-mode-task-cards.md) (task cards and the blocked exit), [0019](0019-goal-mode-call-estimate-and-limit-wait.md) (usage limits), [0009](0009-agents-ask-with-a-marked-block.md) (`oc-ask`), [0008](0008-handoff-to-another-ai.md) (handoff notes), `server/mission.js` (`BLOCK_ACCEPTS`, `BLOCK_NAMES`, `blocksIn`, `foreignBlocks`, `blockPart`, `partName`, `parseReview`, `BLOCKED_KINDS`, `parseBlocked`, `blockedRule`, `outsideRule`, `resumeSent`), `server/orchestrator.js` (`#runAgent`, `#route`, `#failover`, `#nearLimit`, `#missionMsgLines`, `#autoNote`, `#meeting`, `#runStage`, `#failLines`, `#missedInputs`, `#cardsAfter`, `#blockedOf`, `#blockedAsk`, `#prompt`), `public/js/chat-tools.js` (`routeTip`, `agentWrote`), `public/js/views/session.js`, `public/js/views/mission.js` (`MissionLog`), `public/js/state.js`, `test/goal-records.test.js`, `test/mission-review.test.js`, `test/handoff.test.js`, `test/mission-resume.test.js`, `test/fake-cli/fake-claude.js`

## Context

A check of goal mode against what it set out to do found small gaps that each made the record less trustworthy. The criteria check refused a verdict mixed with another block by a pattern that named a block no step uses and missed two that do (`oc-cards`, `oc-research`), and nothing said in one place which step reads which block. When a run went to another AI (automatic routing, a limit close, a takeover) only a notice line said so; the message kept what ran but not what was asked or why. Side work (the automatic handoff note, research during a goal meeting) didn't stop when a subscription limit was close, only when the goal's call count was low. Failures were named `review`, `outside`, `blocked`, `hole` or `keep`: an ordinary error left no log line at all, and nothing told "the earlier card gave me nothing" from any other failure. Agents' answers in a goal's work run looked the same as confirmed text. Nothing told the agents what to ask about before doing it.

## Options

1. Have an AI classify failures, reasons and what to ask about. Costs calls and makes guesses look like facts.
2. Leave the record as it is and document the gaps. Cheap, but the user still can't see who ran, why, or why something failed.
3. Fix the pattern from one table, record only what the code did or saw (and what an agent wrote in a block, marked as such), stop side work first when a limit is close, and add a short written instruction for what to ask about, saying plainly that it is only an instruction.

## Decision

Option 3.

- **Block table** (`BLOCK_ACCEPTS`): goal `oc-goal`, `oc-ask` · scan none · questions `oc-research` · research (also research during a meeting) none · meeting turns `oc-verdict`, `oc-check` · plan `oc-cards` · work stages and task cards `oc-blocked`, `oc-ask` · criteria check `oc-review`. Run-once steps can't ask the user, so only the goal turn and work steps take `oc-ask`. The code that reads each block is unchanged; the table is the single source for the criteria check's mixed-block rule (every block in the table except `oc-review`, so `oc-cards` and `oc-research` are now refused and a name no step uses no longer counts) and for one log line (`kind: 'block'`) when a goal answer has a block its step doesn't take (by the message's marks, `blockPart`). That block is not read; the rest of the answer is handled as before. A block counts only when its opening line starts with exactly three backticks and the exact name, followed by the end of the line or a space (`BLOCK_AT`, and the mixed-block rule the same way): a name written in the middle of a line, a longer name (`oc-research-x`) or an example quoted in the verdict's evidence (a JSON string can't start a line) is not a block. The table is by step, not by turn (see Consequences). A test checks that every block example a step's prompt shows is in the table.
- **Who ran, and why** (`msg.route = { asked, ran, why }` on every agent answer that started): `asked` is the agent's setting (`{ provider: 'auto', model: '', effort: '' }` for automatic routing), `ran` the AI the app started (after a takeover, the AI that took over; the model name a CLI reports back is not used), `why` the codes for what the code did: `auto` (automatic routing), `near-limit` (a limit close or resting, so another AI), `daily-budget` (the day's budget for that AI used up, so another AI; the name the resting list already uses), `daily-pace` (effort lowered for the daily budget, also on the AI that took over), `takeover`, `wait-reset` (waited for a reset that was due soon), `account-gone` (the agent points at a removed Codex account, so the default Codex ran; `asked` keeps the removed account); empty when none. After a wait for a reset, `near-limit` and `daily-budget` are judged from the values after the wait (a limit that has reset and a budget still used up is `daily-budget` only). A takeover sends the new value with `messageMeta`. In a goal run, an answer gets one log line (`kind: 'route'`) only when its reasons include something other than `auto` (decided by the repository owner): an AI picked by automatic routing alone stays in the message's `route` and the chip's title, so a goal of agents on automatic routing doesn't fill the 200-line log. The model chip in the answer's head shows what was asked and why on hover (`routeTip`); when the model is left at the default and there is no model chip, the AI chip carries it; no new element.
- **Side work stops first** (`#nearLimit`, the same test `#route` uses to avoid an AI: resting, or a window at or over the takeover threshold, or a rejected record): the automatic handoff note is skipped with one chat line when the AI that would write it (the AI that made its conversation, else its set AI) is near its limit; research during a goal meeting is turned off when the research agent's set AI is near its limit (`check.status: 'near'`), as it already was when fewer than a quarter of the calls were left. Both are checked again at every turn and every question: the turn's status follows the reason at that moment, and the log gets one line when research is turned off, when the reason changes and when it comes back on (not again while the reason stays the same). The plan and the criteria check are unchanged.
- **Failures by kind**: `oc-blocked` takes an optional `kind`: `unclear` (the instruction is ambiguous), `input` (what was handed over is wrong), `capability` (no permission or tool), `dependency` (other work must finish first); anything else or nothing is `unknown`. The blocked log line keeps it as `agentKind` and the screen shows it next to "written by the agent". The code adds two `fail` values: `input` when a task card ends in an error, a block or a gap after a card it waited for ended without a result (gap, blocked or skipped), and `unknown` for an error that isn't a usage limit (one `kind: 'error'` line per failed person before the error wait; a usage-limit error there is `outside`). The lines of the scan, the research questions, the research note, the plan and the criteria check get `unknown` the same way when their call ended in an error that isn't a usage limit (a usage limit was already `outside`; the research note's one line says `outside` when any question hit a limit). A wait asked again after continuing a cut goal is not logged twice: the error wait skips its error lines, and the blocked wait keeps the cards and blocks judged before the cut as they were and doesn't write their card, `input`, blocked and asking lines again. No kind is guessed.
- **Where it came from**: in a goal's work run, work-stage and task-card answers and meeting conclusions show the goal cards' small "Written by an agent · not confirmed by you" in the answer's head (`agentWrote`; when the run record was trimmed, task-card answers still show it). Answers outside goal mode are unchanged.
- **Ask first** (decided by the repository owner): goal work stages and task cards get one line (also the lead who fixes a meeting stage alone on a return, since that turn runs with the agent's own permission; it doesn't get the blocked exit, which meeting stages don't read): before anything that leaves the PC (pushing to a remote repository, deploying, sending mail or messages, posting, paying) or deleting files outside the work folder, ask with the question block; editing and creating inside the work folder needs no asking. When the run can't ask (asking turned off, a schedule, a session override) the line says not to do those and to note them in the answer. The "[Continuing]" line of 0016 gets "Don't repeat anything already sent outside." The read-only steps (research, meetings, plan, check) don't get the line. The line adds 109 characters to each work prompt in Korean (255 in English), the continuing line 22 (44); the blocked exit's kind line adds 165 (291).

This adds `route` to messages (with the reason codes above), `near` to `check.status`, `kind` to `oc-blocked`, `kind` to the blocked items of the `mission/blocked` hold, the log kinds `block`, `route` and `error`, the `fail` values `input` and `unknown`, and `agentKind` on log lines. Older versions ignore them; their screens show no chip for the new `fail` values and the plain `near` status text.

## Consequences

- The record now says who was asked for and who ran, and names failures only by what the code saw or what an agent wrote in its block. The user can tell side work that was skipped for a limit from work that failed.
- Not covered: "ask first" is a written instruction; nothing in the code stops an agent from pushing, deploying, sending or deleting. The agent's own permission and the CLI's settings still decide what it can do.
- Not covered: a CLI that resolves a model alias (for example "opus" to a full name) is recorded with the name the app asked for.
- Not covered: the block table is by step, not by turn. Inside a step, a block that the code reads only on another turn of that step isn't read and gets no log line: `oc-verdict` on a meeting opinion, turn or conclusion, `oc-check` on a judge turn, opinion or conclusion, `oc-ask` on a work turn or the goal turn that can't ask (asking turned off, a schedule, a session override), and `oc-blocked` from the lead fixing a meeting stage on a return. Telling these apart would need per-turn facts (whether that run could ask) that the message doesn't carry; such blocks are only ignored, as before.
- Not covered: whether an agent's `kind` is right is not checked. `input` from the code means only that the earlier card had no result, not that this caused the failure. Research turned off for a near limit looks at the research agent's set AI; an agent on automatic routing is not checked, since where it would go isn't known before it runs.
- Not covered: the handoff note skip repeats its chat line for each request while the limit stays close.
- Screens checked in a real browser (fake Claude and Codex CLIs, a temporary data folder): the model chip's title on a goal answer on automatic routing and on an ordinary answer moved for a limit close (read from the page; the browser's own tooltip box doesn't show in screenshots), "Written by an agent · not confirmed by you" on a pre-work meeting's conclusion, work-stage and task-card answers and not on the goal draft, meeting opinions and turns, the plan or the criteria check, and not on an ordinary answer; the progress tab's route line, "Cause unknown", "Handed over" (since renamed "Missing input"), and "Blocked" with "Needs other work first · written by the agent"; the "research off: near the limit" chip under a meeting turn; Korean and English. Not checked on screen: Simplified Chinese and Japanese (the translation test only), a dark theme, a narrow window, the handoff-note skip line, and the block line for a block a step doesn't take (tests only).
- The fake Claude for tests reads `WORKFOREIGN` (a work answer ends with an `oc-research` block), `BLOCKKIND:<value>` (the blocked block carries that `kind`), `NEARLIMIT` (a successful answer reports a 5-hour window at 97%) and `K2BLOCK` (task card k2 ends with a blocked block too).
- To undo: drop the `BLOCK_ACCEPTS` checks and `#missionMsgLines`; the stored fields are then unused.
