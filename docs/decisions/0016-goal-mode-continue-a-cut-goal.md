# 0016: A goal cut off by closing the app continues from where it stopped, only when the user asks

- Status: Accepted
- Date: 2026-11-20
- Related: [0014](0014-goal-mode-confirmed-goal-card.md) (the goal card, the restart rule), [0015](0015-goal-mode-fresh-review.md) (the criteria check, returns, the waits and the call cap), [0010](0010-meetings-take-turns.md) and [0011](0011-meetings-pause-for-research.md) (meetings and their research turns), [0012](0012-claude-usage-counts-the-whole-tree.md) (usage baseline), [0013](0013-agents-keep-role-notes.md) (role-note hash), `server/mission.js` (`stageDiff`, `sameStages`, `teamRoles`, `resumePoint`, `pastOutputs`, `cutMission`), `server/orchestrator.js` (`resumeMission`, `confirmMission`, `#start`, `#missionRun`, `#missionWork`, `#runStage`, `#missionAt`, `#atWorking`, `#runAgent`, `#capCheck`, `#missionAsk`, `#reviewStage`, `#stagePrev`, `#prompt`, `#missionEnd`, `stopAll`, `recover`, `send`), `server/store.js` (`#fixStale`), `server/index.js` (`POST /api/sessions/:id/mission/resume`), `public/js/views/mission.js` (`CutBox`, `resumeFrom`), `public/js/views/session.js`, `test/mission-resume.test.js`

## Context

Office Crew starts the CLIs itself, so when the app closes while a goal runs, the run is gone. Since 0014 such a goal turns `cut` at the next start and can only be discarded: the user sends the request again, and every stage, and the calls they cost, start over even when most of the work was done. Continuing needs to know where the run was, what the earlier stages produced, who was cut in the middle of a turn, and what to do with their CLI conversations.

## Options

1. Start again automatically at the next start. The user may not want it (they closed the app for a reason), and it can spend calls with nobody watching.
2. Continue from the start of the run, keeping the goal. Simple, but repeats every stage.
3. Record the point in the run as it moves, and on the user's request start a new run at that point, gathering the earlier answers from the session.

## Decision

Option 3.

- **The cut point** (`mission.at = { stageIndex, phase: 'work'|'review', back, working, finished, wait }`), saved at once each time it changes. The run writes the stage and phase when a stage starts, when a work stage ends (the next point: the next work stage, or the criteria check after the last work stage or after a return), when the criteria check starts, when a return is decided (before its pause or cap check), when a stage runs again after "retry" or "reject", and when it starts waiting: `wait` is `{ reason: 'approve' }`, `{ reason: 'error', failed: [{ agentId, error }] }`, `{ reason: 'mission', kind: 'verdict'|'notes' }` or `{ reason: 'cap' }`. `working` is kept per agent: an agent goes in when its CLI starts (a meeting's research agent too, even from another stage, and the reviewer) and comes out when the call ends, unless the app or the user stopped it. `finished` lists the answers finished in this attempt of the stage (for a meeting, its conclusion). Confirming writes the first point, the team stage numbers the user kept (`mission.keep`), the work folder (`mission.cwd`) and each team member's kind of role (`mission.roles`). A restart turns the goal `cut` as before and leaves `at` as it was. When the app closes normally (`stopAll`), a closing mark keeps the run's end from changing the goal's status, so the goal is `cut` after the restart whatever order the shutdown steps happen in.
- **Only on request**: nothing starts at app start. `POST /api/sessions/:id/mission/resume { missionId }` continues; the card's cut notice, the progress tab and the box above the message field show **Continue** (main button) and **Discard**, a line saying where it starts again (which stage, a return, a meeting from round 1, the same question with no AI call; only the cut agents start a new conversation), and the reason when continuing is refused (shown in all three places).
- **When it is refused**: 409 for another goal's id, a goal that isn't `cut` (discarded, ended, already continuing), a run going in the session, a missing request message, a goal without a cut point or kept stages (cut before this record), a missing record of the cut run, and a changed team, with the reason saying what changed: the work folder, an agent's kind of role, or the stage list rebuilt from the current team with the kept stages (`#missionPlan`), compared with the cut run by number of stages, criteria check position, labels, agents in order, approval gates, meeting or not, meeting settings (rounds, chair, opposing side, usage cap) and stage instructions (`stageDiff`; the check's own label is not compared, it is named in the app language), and the reviewer. An agent's AI, model and permission are not compared: the agent runs with what it has now. 400 when the team check of 0014 fails now (a model on this PC mixed with cloud AIs). The goal stays `cut` after a refusal. Trimming a session's run list to the last 30 keeps the work runs of a goal that is still alive (cut included).
- **The new run** (`resumed: true`) starts at the cut point. Earlier stages don't run again; their results are gathered from this goal's earlier work runs (`pastOutputs`): for each stage and agent, the latest finished answer (for a meeting stage, the latest conclusion or the lead's lone fix on a return), without review answers, goal drafts and handoff notes. The log names stages with nothing found; a stage that was skipped is not counted as missing. Earlier stages show as they ended.
- **Where it starts**: a work stage → that stage: the answers in `finished` are used as they are and those agents don't run again; the others run (a meeting runs again from round 1). A return → the same return, with the failed criteria block and the stage's previous result, without counting another return. The criteria check → the check again, counted as the same round. An approval or error question → the same question again with no AI call, from the saved answers (and, for an error, the saved error lines); approving, retrying, rejecting and skipping then work as before (retry and reject run the whole stage). A verdict or notes question → the same question again with no AI call. The call cap → the same cap question before that stage with no AI call.
- **Who starts fresh**: before the run starts, the agents still in `working` of a work stage lose this session's `providerSessions`, `sessionProvider`, `usageBase` and `noteHashes` entries, so they start a new CLI conversation (the earlier conversation comes back as `[Previous conversation]`, as for any agent without one). For a meeting stage that is every participant plus a research agent that was working. Their first call in that stage, and no other call, begins with one code-written line: "[Continuing] This stage was cut off midway because the app closed. First check whether the work folder already has work done for it, and if so, continue from there." Agents that finished, hadn't started (for example waiting for a usage limit) or were waiting at a question keep their conversations. The reviewer of a cut criteria check is left alone: the check never reads or writes its conversation (0015).
- **Carried over**: calls (`calls.used`, `cap`), `returns`, `returnCap`, `round`, criteria verdicts, and notes already used (they keep going into later stages; unused ones are asked about as before). The log gets `resume` lines: where it starts, who starts fresh, which finished answers are reused, and the gathered results. A goal can be continued again if it is cut again.
- A stopped run read back from disk also shows its running or approval-waiting stage as stopped (`#fixStale`, and the same for runs in memory at restart), for goal runs and others.

## Consequences

- A cut goal costs only the calls that were cut (or nothing, at a question) instead of the whole run again. The session file is written a few more times per goal run (each CLI start and end, each stage start and end, each wait); this cost is not reduced.
- Not covered: what a cut CLI left half done (a half-written file, a command that didn't finish) is not detected; the agent is told to look at the work folder and decide.
- Not covered: a meeting cut in the middle runs again from round 1 with every participant in a new conversation; the turns said before the cut are not reused.
- Not covered: the usage of a cut call isn't counted (the CLI never reported it), and a call started in the last fraction of a second before the cut may be missing from the call count. If the app is killed before the session list was saved as running, the chat line about the cut is not written (the goal is still `cut` and can be continued).
- Not covered: a goal cut while the lead was drafting the card is still closed (there is no draft); the request has to be sent again. A goal cut before this change has no cut point and can only be discarded.
- Not covered: in a narrow window the box above the message field can be covered by the side panel; the goal card and the progress tab show the same buttons.
- Not covered: how real CLIs pick up the work from the folder is not measured; the tests use fake CLIs and simulate a crash by freezing the data folder (the test file's head comment lists how that differs from a real one).
- Screens checked in a real browser: with the demo agents (no AI usage), by killing the app and starting it again on the same data: a goal cut during the review (the cut notice with Continue and Discard in the progress tab and above the input, continuing runs only the review and the call count goes on), a goal cut during a work stage (the earlier stage is not run again, the cut stage starts a new conversation, the progress lines say what was gathered), and a goal cut while waiting for an approval (continuing asks the same approval again with no new call). Nothing started by itself after the restart. Not looked at: a goal cut in a parallel stage, in a meeting, at the verdict, call cap and late-instruction questions, the refusal when the team changed, a normal quit, the English, Chinese and Japanese screens, the dark theme and a narrow window
- To undo: drop the resume route and `CutBox`'s Continue button; `mission.at`, `keep`, `cwd` and `roles` are then unused and harmless, and the closing mark only keeps a goal resumable.
