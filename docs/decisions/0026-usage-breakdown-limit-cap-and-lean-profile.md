# 0026: Usage is shown split and weighted, a goal asks before new work when a subscription window is over a cap, and a lean profile hands on less

- Status: Accepted
- Date: 2026-11-26
- Related: [0008](0008-handoff-to-another-ai.md) (the whole-conversation file and its folder), [0012](0012-claude-usage-counts-the-whole-tree.md) (what a message's usage counts), [0015](0015-goal-mode-fresh-review.md), [0017](0017-goal-mode-research-and-meeting-first.md) and [0019](0019-goal-mode-call-estimate-and-limit-wait.md) (revised here), [0022](0022-goal-mode-records-and-block-allow-list.md) (side work stops first near a limit), [0023](0023-prompt-assembly-for-cache-and-fresh-meeting-turns.md) (the prompt measurement), `public/js/usage-numbers.js` (`weighted`, `split`, `cacheHit`, `useKind`, `usageBreakdown`, `overCap`), `server/savings.js` (`LEAN`, `leanTurns`, `prevTail`, `prevNote`, `noteNote`, `writeNote`, `noteSummary`), `server/orchestrator.js` (`meetingSpend`, `fixedText`, `#limitCheck`, `#capTarget`, `#quotaAsk`, `#prompt`, `#notePart`, `#withHistory`, `control`), `server/mission.js` (`researchNote` `show`, `resumePoint`), `server/index.js` (`POST /api/agents/fixed-text`, settings), `server/store.js` (`attentionOf`), `server/notify.js`, `public/js/stage-model.js`, `public/js/views/` (`session.js`, `settings.js`, `usagedock.js`, `mission.js`, `manage.js`, `routing.js`), `test/usage-guard.test.js`, `test/fake-cli/fake-claude.js` (`LONGANSWER`), `test/measure/prompt-audit.js` (`--savings`)

## Context

- The screen added input, output, cache reads and cache writes 1:1. A Claude call that mostly reads the cache then looks far bigger than it is: the test CLI's call (10 new input, 50 cache writes, 100 cache reads, 5 output) showed 165 tokens, while the meeting usage limit already counted the same call as 75 (cache reads ÷ 10, `meetingSpend`). Nothing showed where a session's usage went (goal turn, research, meetings, plan, cards, check) or how much fixed text an agent sends with every new conversation (0023 measured 20,686 characters of skill bodies for the default research agent).
- Subscription windows were shown (0019) and an AI near its limit was avoided (95% by default), but a goal kept starting new work on an AI at 92% when no other AI could take it, until the limit stopped it mid-step. The repository owner decided to add a cap now, 90% by default.
- In the measurement of 0023 (test CLIs, characters, measured again for this record), a goal run with research, a meeting and four task cards sent 224,187 characters, 53,624 of them (24%) copies of the research note; an agent taking over a long session got 16,512 characters of `[Previous conversation]`; a three-stage run gave the last stage every earlier result in full. The owner decided on a lean profile that is off by default and switches all three at once.

## Options

1. A token budget per goal. Tokens per call vary by a wide margin and percentages differ by plan (0019 rejected a forecast for the same reason); a budget would stop work on a number nobody can predict.
2. Show usage split and weighted from one shared function, ask before new work by the percentages the app already receives, and offer a lean profile that cuts the three biggest handed-on blocks while leaving the criteria check alone.
3. Cut always (no profile). Saves the most, but changes what every agent gets without the user choosing it.

## Decision

Option 2.

1. **Usage split and weighted** (no AI call). `weighted(u)` = new input + cache writes + output + round(cache reads ÷ 10) lives in `public/js/usage-numbers.js`; `meetingSpend` in the server is that same function. Every single number on screen is labelled "weighted" (the bottom-right indicator and its "today", the Usage page, the session's Usage & limits tab, under each message, the run bar, the inspector and the team cards), and the four parts and the 1:1 sum are shown next to it or in its tooltip. The office name tags keep the 1:1 sum (that renderer has its own labels; not changed here). The Usage page lists each AI's four parts and, per agent, the cache hit rate (cache reads ÷ (new input + cache reads + cache writes)), shown only when the agent has cache numbers at all. The session's tab gets "Where it went": weighted usage and answer count by kind (ordinary run, set the goal, research = scan·questions·research, meeting = every meeting turn and the pre-work meeting, plan, task cards with their closing-line retries, review), read from the marks messages already carry (`useKind`), and by agent with cache hit rate; "This goal only" keeps the runs of the session's goal. Nothing new is stored. The agent editor shows the fixed text sent with every new conversation: `POST /api/agents/fixed-text` builds the agent's system instructions from the values being edited (`#system`, notes picked without a request, the default work folder) and returns the character count (code points, not tokens) and the skill share (with skills minus without); from 10,000 characters of skill bodies a line says they go into every new conversation. The screen never receives skill bodies.
2. **Subscription cap** (`limitCap`, 90 by default, 0 = off, Routing page). In a goal's work run, right after the call-cap check and before new work starts (scan, questions, research, pre-work meeting, plan, a work stage or task card step, the criteria check, and the next pass after a block's "once more"), `#limitCheck` looks at the AI each starting agent will actually run on (`#capTarget`: the same choice `#route` makes, without waiting or state changes; moving to another AI near a limit comes first, an AI that will wait for a reset that is due soon (`waitForResetMin`) is skipped). If a window of that AI's received record has a numeric percentage at or above the cap and hasn't reset (`overCap`; a record the user released is ignored), the run waits (`hold.reason: 'limitcap'`, the box of the other goal waits): **Continue** (that AI goes into `mission.capOk`; no more asks about it in this goal, also after a cut) · **Continue after the reset** (only when every window over the cap has a reset time; the timer `quotaDelay` and the count `mission.quota.autos`/`QUOTA_AUTO` of 0019 are shared; when it fires the record is checked again and the count rises only if work starts; a pause pressed meanwhile is honoured first) · **Stop**. AIs that report no percentage are not checked. To avoid asking twice about one limit: choosing anything but Stop in 0019's usage-limit wait also puts that AI in `capOk`, the retry after a limit wait doesn't check, and a wait continued after a cut doesn't check. The cut point is `wait: { reason: 'limitcap' }`; continuing reaches the same check again and asks without an AI call (and starts if the record no longer shows the AI over the cap). The goal card's limit line shows the cap and marks AIs already over it; the flow stage draws the gate before the stage, inside it when the server marks the wait `ran`, and an auto-continue shows as a limit wait, not your turn; the sidebar, notices and phone notifications name the kind `limitcap`.
3. **Lean profile** (`savings: 'normal' | 'lean'`, normal by default, Settings → Defaults). With lean: (a) an agent starting a conversation gets `[Previous conversation]` for half of `historyTurns`, rounded up, at least 1 (`leanTurns`; 0 stays 0; the missed conversation, the API history and the long-session test are unchanged); (b) a goal's research note is written to `handoff/<session>/research/<goal>/note-work.md` (instruction-like lines left out, as for work stages) or `note-meeting.md`, answers not cut, with a fixed marker per goal so the same note isn't rewritten; an AI with file tools gets that folder opened for the run (as the conversation file of 0008) and, in the prompt, the note's head lines, one notice line, the path and each answer's first line (160 characters, the list 2,000 at most); an AI without file tools, or a file that can't be written, gets the note as before; the plan step keeps the whole note; (c) `[Previous stage results]` give the last earlier stage with output in full and earlier stages their last 1,500 characters (`prevTail`), with one notice line under the heading when something was actually cut. The criteria check's material, a return's previous result and a card's input cards are not reduced.
4. **Fixed prompt size**: normal adds nothing (the measurement below sends the same characters as the parent commit). Lean adds only its notice lines: "Of the earlier stage results…" (70 characters in Korean, 160 in English) once per prompt where earlier results were cut, "The research note shows only the first line…" (40 / 98) once per research-note summary, and the "…(beginning left out)" mark (9 / 21) per cut result.

This adds the settings `limitCap` and `savings`, `mission.capOk`, the hold reason and cut-point wait `limitcap` (hold fields `phase`, `cap`, `until`, `canAuto`, `autos`, `autoMax`, `autoAt?`, `ran?`, `who: [{ agentId, name, provider, ai, windows }]`), the attention kind `limitcap`, the log kind `limitcap`, the `control` actions `accept`·`later`·`retry`·`stop` for that wait, and the research note files in the data folder. Older versions ignore the settings and `capOk`; a goal cut at the cap question can't be continued by an older version (its `resumePoint` doesn't know the wait) and can only be discarded there.

## Consequences

- The screen's one number is closer to what a call costs in time and limit, but it is a weight, not a price list; Codex's continued conversation shows up mostly as cache reads, so it now looks smaller than before.
- Not covered: a cap for ordinary runs outside goal mode; a token budget; giving skills by name only (left for later, as in 0023); a cap when no percentage was ever received (the record must come from earlier runs, it can be old, and a window that reset is taken as reset).
- Risk: lean hands on less, and answers can get worse (an earlier stage's beginning, half the conversation, a research answer beyond its first line). Whether an AI reads the note file is its own choice; the quality effect was not measured with a real AI, only prompt sizes with the test CLIs. The criteria check is kept whole for that reason.
- Risk: a goal on an AI already over the cap now stops before every first step until the user answers (once per AI per goal); existing installs get the cap at 90% when they update.
- To undo: set `limitCap` to 0 and `savings` to normal (both are settings); to remove the code, drop the `#limitCheck` calls and `#notePart`/`prevTail`/`leanTurns` in the orchestrator, and draw `usageTotal` again on screen. The stored fields can stay.
- Screens checked in a real browser (test CLIs, a temporary data folder, a port other than 4317): the goal card's limit line with the cap and the "over the cap" chip, the cap question with its three choices and the gate before the stage on the flow stage, "Continue" running the goal to the end, "Continue after the reset" turning the pill into a limit wait with time left on the person, the session tab's split numbers and "Where it went" with and without "This goal only", the Usage page's split and cache hit rate, the agent editor's fixed-text line and warning, the lean switch in Settings and the cap card on the Routing page, English, a dark theme, a phone-width window (the agent table's header overlapped there and was fixed). Not checked on screen: Simplified Chinese and Japanese (the translation test only), a goal cut at the cap question and continued (tests only), the research note file being opened by a real CLI.
