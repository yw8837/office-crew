## Revision (2026-11-25, with [0019](0019-goal-mode-call-estimate-and-limit-wait.md))

A criteria check that ends with a usage limit and no other AI to take over no longer ends without a verdict: the run asks with the usage-limit wait of 0019 (continue after the reset time automatically, retry now, accept without a verdict, or stop), a retry runs the same round again, and the call cap is checked before it. Of the stages, only work stages (team stages and task card steps) get the same wait instead of the error wait; research, meetings and the plan keep their handling. The goal card now shows a rough estimate of the whole goal's calls before confirming (0019); tokens and subscription percentage are still not capped. The sentences below about the limit case and "no estimate before starting" describe the earlier behaviour.

## Revision (2026-11-22, with [0018](0018-goal-mode-task-cards.md))

From outside sources (a study where an evaluator found problems and then talked itself into passing; a talk and a public set of agent playbooks that block only on failures that can be shown and send the rest to a follow-up list; reward-hacking studies where giving the agent a way to stop cut cheating far more than telling it not to cheat):

- **Rules in the check prompt**: a problem that breaks a criterion is `fail` even if it looks minor (the user decides whether to let it go); `fail` only for a breach shown by running or reading something, and a `fail` without evidence is read as `unknown` (as a `pass` without evidence already was). Problems seen outside the criteria are not `fail`: the block has `extras` (one line each, up to 5, 200 characters), shown as "Follow-ups" in the progress tab and in the verdict box and never blocking. When the goal has **keep** items ([0014](0014-goal-mode-confirmed-goal-card.md)), the block has `keepBroken` (what was broken, with evidence); anything there is logged as "broke what had to stay" (`fail: 'keep'`) and the run asks even if every criterion passed (no automatic return; accepting then ends `accepted`, not `done`). Copies of the example lines are dropped. A verdict answer with an `oc-cards` or `oc-blocked` block is not accepted.
- **Changed files**: when the work folder is a git repository, `git status --porcelain` (up to 50 lines; run with the repository's `core.fsmonitor` turned off and without optional locks, so a repository setting can't start a program) goes into the check inside random markers, with "if test files changed, check that the change didn't weaken the criteria"; changed files with `test` or `spec` in their path get a log line. Without git, outside a repository, or after 5 seconds without an answer, nothing is added and nothing fails.
- **The reviewer's permission on the card**: the review line says "read-only, so it can't run commands or tests; it judges only as far as reading the files shows" or "it can run commands and tests to check". It is information only (not part of the confirm comparison); the app still doesn't raise or lower the reviewer's permission.
- **Assumption line**: when a return is the second (`returns ≥ 2`) or the same criterion failed in two rounds in a row, the return prompt ends with a code-written line: "[Write down the assumption] The earlier fixes may have shared an assumption. First write in one sentence what every attempt assumed, check it yourself, and then fix." (logged once).
- **Gaps**: a check whose block was missed twice is logged as a gap (`fail: 'hole'`); as before it counts as no verdict (every criterion `unknown`), never as a pass.
- **Blocked exit**: a goal's work stages (stage list mode included) can end with `oc-blocked`; the run then asks before the check (0018).

## Context

After 0014 a goal run did the team's stage list with the confirmed goal attached and ended `unreviewed`: nobody had checked the criteria. A team's own review stage is an agent reading earlier answers and writing an opinion; it can repeat "all done" from an earlier stage, its verdict can't be told apart from text it copied, and nothing acts on a "fail". The goal needs a check per criterion that the code can read, a bounded way to fix what failed, and a point where the user decides.

## Options

1. Keep the team's review stages and parse their answers. Their prompts and conversations are shared with the rest of the run, and a verdict written by a work stage (or copied from a web page) would look the same.
2. Ask the user to judge every criterion. Safe, but the user gets back the work the goal was meant to take off them.
3. A separate criteria check at the end of the run by a team member who didn't do the last work stage, run once with a prompt built by the code and a one-time value; at most one automatic return to the last work stage; anything left goes to the user.

## Decision

Option 3.

- **Who reviews** (`reviewPlan`, computed on the team when the card is drafted and again when it is confirmed): a review stage is a stage whose agents all have a review role. The reviewer is the first agent of the team's review stages who isn't the lead (even if that agent also works in the last work stage, in a stage with mixed roles), else the first team member who isn't the lead and isn't in the last work stage, else nobody. Never someone outside the team (so a team of only local models keeps a local reviewer, 0007). The last work stage is the last remaining stage that isn't a review stage (or the last remaining stage).
- **Which stages the check replaces**: review stages without an approval gate that aren't meetings can be skipped, unless that would skip every stage. The card shows "Review: X judges each criterion" and each such stage with a **Keep** box and the first 120 characters of its instructions (skipping a stage skips its instructions too); nothing is skipped without the user seeing it. Confirming sends `review: { reviewerId, droppable, drop: [team stage numbers] }`, `droppable` being the list the card showed (number, label, agents, instructions); when the reviewer differs from the server's value, the list isn't the same as the one computed now character for character (so a team edited after the card can't make the same number mean another stage), or `drop` isn't a subset of what can be skipped, the answer is 409 with the current `review` and nothing starts. A request without `review` (an older screen) skips nothing. The goal stores `reviewerId` and the skipped labels (`dropped`) and logs both.
- **Run shape**: one run = the remaining team stages + a last stage `{ label: "Criteria check", agentIds: [reviewer], mission: 'review' }` when there is a reviewer. The body of a stage moved out of the main loop (`#runStage`); runs outside goal mode use it unchanged (prompts and events are the same; the fixed-prompt test still passes).
- **Run once**: the reviewer starts a new CLI conversation and the session keeps none of it: no conversation id read or saved, no usage baseline read or written (the call is counted on its own, 0012), no role-note hash, no earlier conversation, missed conversation, handoff note, whole-conversation file, project memory or API history, no question card, no queued instructions, and the answer isn't stored in project memory. The system prompt (role, permission, role notes) is the usual one without the "how to ask" part. Empty-answer retries and limit takeovers reuse the same prompt. Budget and auto-routing treat it as a review (no lowered effort, other AI preferred); the "same AI reviews" notice applies whatever the role.
- **Prompt** (`reviewPrompt`): the confirmed goal, criteria with ids (`c1`…), out of scope, work folder, which review round, the latest answer of each remaining work stage inside random markers as reference (first 1,500 characters, "check the rest in the work folder"), a permission line (read-only: "you can't run commands; only what you read is a pass"; otherwise "you may run commands and tests; don't change files"), "only what you checked yourself is a pass, otherwise unknown; don't ask", a 16-hex one-time value and the block format. Extra instructions sent during the goal aren't given to the reviewer. An instruction sent from the panel to the agent doing the check (or waiting for a usage limit before it) is not put into the check either: it becomes one of the goal's extra instructions (a chat message and a log line saying so), so it is asked about after the verdict. In a goal's work run, an instruction to an agent that isn't working right now is handled the same way, and the log says how each instruction was actually handled (put in now, after the current work, at the start after a limit wait, or taken as an extra instruction).
- **Accepting a verdict** (`parseReview`): one fenced `oc-review` JSON block, last in the answer and closed, with the one-time value; no other `oc-` block anywhere in the answer. Ids are read without regard to case (`C1` is `c1`), unknown ids are dropped, missing ids are `unknown`, verdicts are read lower-case and anything but `pass`/`fail`/`unknown` is `unknown`, a `pass` without evidence is `unknown`, the same id twice keeps the worse one (fail > unknown > pass). The criterion text is the code's, never the model's. Otherwise the check is asked once more with a new value (a new message); if that fails too, or the reviewer ends in an error or is skipped, there is no verdict and every criterion is `unknown`. A stop ends the goal.
- **After the verdict**, in order: stopped → `stopped`; unused extra instructions → ask (use them and go again / end as is / stop); all pass → `done`; a `fail` and returns left (one at first) → automatic return; else ask (accept / once more / stop; once more isn't offered without a reviewer). A return runs the last work stage again with the failed and unknown criteria and their evidence in a random-marker block "[What failed in the last review — reference]" (evidence 300 characters, `<` `>` full-width), not as user feedback, and with that stage's previous result (each agent's own answer; for a meeting, its conclusion) in a random-marker block "[This stage's previous result — reference]" unless the agent continues the CLI conversation that wrote it; a meeting stage is redone by the lead alone (with the conclusion), and an approval stage asks for approval again (an automatic return doesn't skip a gate the user set). Then the check runs again; stages after the redone one (kept review stages) don't run again, so the next check leaves their old answers out and says so, and the log says which stages that is. "Once more" (after a verdict or about unused instructions) allows exactly one more return (`returnCap = returns + 1`): if the stage still fails, the run asks again instead of returning by itself. `done` is written only when every criterion is `pass` and no question is open; accepting otherwise ends `accepted` with the verdicts kept.
- **Waits**: two new hold reasons, `mission` (`kind: 'verdict'|'notes'`, round, the criteria left, unused notes, `more: false` and `reviewer: false` without a reviewer) and `cap` (with `step`, the number "more" adds), answered with the new `control` actions `accept` and `more` (or `stop`). Another action gets `{ ok: false }`. The goal is `waiting` meanwhile; the sidebar, notices, desktop and phone notifications name them as their own kinds (`verdict`, `cap`), the stage strip shows the waiting stage as waiting, and the chat scrolls the box's head into view when it opens (only while following the bottom). A restart turns such a run `stopped` without a hold (by status, like any waiting run) and the goal `cut`. An extra instruction sent while a team without a reviewer waits at a verdict gets `late: true`, because "once more" isn't offered there.
- **Call cap**: each CLI start in a goal counts (`calls.used`, from the goal turn, including retries, takeovers, empty-answer retries and answers to questions). Before each work stage and the check, if `cap - used` is less than the stage's people (for a meeting stage, the meeting's call count, [0017](0017-goal-mode-research-and-meeting-first.md)), the run asks: 20 more / stop. The cap is 40 (`MISSION_CALL_CAP`); there is no setting yet.
- **The answer is not the agent's conversation**: a review answer (like a goal draft) isn't counted as the agent's own last answer when finding the conversation it missed, in the history list of agents without a resumable conversation, or when choosing who writes a handoff note; the agent's own review answers are passed to it as conversation it missed.
- **Records**: the review answer keeps `review: { round, results: [{ id, verdict, evidence, text }], missing, retried }` and the block's span; the screen hides the block and shows a table marked "written by an agent · not confirmed by you". The goal keeps `round`, `returns`, `returnCap`, `calls`, and each criterion's `status`/`evidence`. Log lines for the check, the return, the questions and answers, the cap; a failing check line carries `fail: 'review'`, a check that hit a usage limit `fail: 'outside'`. Older data with `unreviewed` is read as an end state.
- The demo provider recognizes the check by its exact head and closing block example and answers with a block (`REVIEWFAIL`, `REVIEWFAIL2`, `REVIEWUNK` in the goal sentence change the verdict), so the flow can be tried at no usage.

## Consequences

- A goal costs at least one more call (two when the format has to be asked again), and a return costs the last work stage again plus another check.
- Not covered: the reviewer runs with its own permission setting; "don't change files" is an instruction, not enforced. To let it run tests, the user raises that agent's permission.
- Not covered: a reviewer from the same AI company as the workers is only flagged (the existing notice), not prevented. A review-role agent that also works in the last work stage (a stage with mixed roles) can be picked and then checks its own work.
- Not covered: the cap is checked before a stage starts, against the number of the stage's agents (a meeting stage, and the pre-work meeting of [0017](0017-goal-mode-research-and-meeting-first.md), against the meeting's call count); retries and takeovers inside a stage, and research turns during a meeting, can go over it. Every meeting turn in a goal run now uses this run-once mode (0017). Tokens and subscription percentage aren't capped, and there is no estimate before starting.
- A goal cut by an app restart can be continued from where it stopped, including at a verdict or call cap question and during a return ([0016](0016-goal-mode-continue-a-cut-goal.md)). Not covered: the criteria can't be changed after confirming.
- Not covered: how reliably real CLIs write `oc-review` blocks, and how honestly they judge, is not measured; the tests use fake CLIs only.
- Not covered: only the last work stage is redone on a return; kept review stages after it don't run again. A meeting's return is one person's answer, not a new meeting.
- Screens checked in a real browser: with the demo agents (no AI usage): the review line and the Keep box on the goal card, a review stage with an approval gate staying and still asking, one failed criterion returning by itself and passing on the second review, two failed reviews opening the question (accept, once more, stop) and each of the three answers, a team with no one to review asking without "once more", keeping the review stage with the Keep box, an extra instruction sent late opening "use it and go once more", the verdict tables in the chat, the progress tab with the chips, the reviewer and the call count, and the waiting mark on the stage strip. Not looked at: the call cap question, the card redrawn after a 409, the notice for a broken verdict block, the approval asked again on a return, an instruction sent to the reviewer, the English, Chinese and Japanese screens, the dark theme and a narrow window
- To undo: confirm without `review` and drop the review stage from `#missionPlan`; goals then end after the stage list (the old `unreviewed` path would have to be put back in `#missionEnd`).
