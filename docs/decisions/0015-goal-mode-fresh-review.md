## Context

After 0014 a goal run did the team's stage list with the confirmed goal attached and ended `unreviewed`: nobody had checked the criteria. A team's own review stage is an agent reading earlier answers and writing an opinion; it can repeat "all done" from an earlier stage, its verdict can't be told apart from text it copied, and nothing acts on a "fail". The goal needs a check per criterion that the code can read, a bounded way to fix what failed, and a point where the user decides.

## Options

1. Keep the team's review stages and parse their answers. Their prompts and conversations are shared with the rest of the run, and a verdict written by a work stage (or copied from a web page) would look the same.
2. Ask the user to judge every criterion. Safe, but the user gets back the work the goal was meant to take off them.
3. A separate criteria check at the end of the run by a team member who didn't do the last work stage, run once with a prompt built by the code and a one-time value; at most one automatic return to the last work stage; anything left goes to the user.

## Decision

Option 3.

- **Who reviews** (`reviewPlan`, computed on the team when the card is drafted and again when it is confirmed): a review stage is a stage whose agents all have a review role. The reviewer is the first agent of the team's review stages who isn't the lead, else the first team member who isn't the lead and isn't in the last work stage, else nobody. Never someone outside the team (so a team of only local models keeps a local reviewer, 0007). The last work stage is the last remaining stage that isn't a review stage (or the last remaining stage).
- **Which stages the check replaces**: review stages without an approval gate that aren't meetings can be skipped, unless that would skip every stage. The card shows "Review: X judges each criterion" and each such stage with a **Keep** box; nothing is skipped without the user seeing it. Confirming sends `review: { reviewerId, drop: [team stage numbers] }`; when the reviewer differs from the server's value or `drop` isn't a subset of what can be skipped, the answer is 409 with the current `review` and nothing starts. A request without `review` (an older screen) skips nothing. The goal stores `reviewerId` and the skipped labels (`dropped`) and logs both.
- **Run shape**: one run = the remaining team stages + a last stage `{ label: "Criteria check", agentIds: [reviewer], mission: 'review' }` when there is a reviewer. The body of a stage moved out of the main loop (`#runStage`); runs outside goal mode use it unchanged (prompts and events are the same; the fixed-prompt test still passes).
- **Run once**: the reviewer starts a new CLI conversation and the session keeps none of it: no conversation id read or saved, no usage baseline read or written (the call is counted on its own, 0012), no role-note hash, no earlier conversation, missed conversation, handoff note, whole-conversation file, project memory or API history, no question card, no queued instructions, and the answer isn't stored in project memory. The system prompt (role, permission, role notes) is the usual one without the "how to ask" part. Empty-answer retries and limit takeovers reuse the same prompt. Budget and auto-routing treat it as a review (no lowered effort, other AI preferred); the "same AI reviews" notice applies whatever the role.
- **Prompt** (`reviewPrompt`): the confirmed goal, criteria with ids (`c1`…), out of scope, work folder, which review round, the latest answer of each remaining work stage inside random markers as reference (first 1,500 characters, "check the rest in the work folder"), a permission line (read-only: "you can't run commands; only what you read is a pass"; otherwise "you may run commands and tests; don't change files"), "only what you checked yourself is a pass, otherwise unknown; don't ask", a 16-hex one-time value and the block format. Extra instructions sent during the goal aren't given to the reviewer, and an instruction sent to the reviewer from its panel goes to the next stage instead.
- **Accepting a verdict** (`parseReview`): one fenced `oc-review` JSON block, last in the answer and closed, with the one-time value; no other `oc-` block anywhere in the answer. Unknown ids are dropped, missing ids are `unknown`, verdicts are read lower-case and anything but `pass`/`fail`/`unknown` is `unknown`, a `pass` without evidence is `unknown`, the same id twice keeps the worse one (fail > unknown > pass). The criterion text is the code's, never the model's. Otherwise the check is asked once more with a new value (a new message); if that fails too, or the reviewer ends in an error or is skipped, there is no verdict and every criterion is `unknown`. A stop ends the goal.
- **After the verdict**, in order: stopped → `stopped`; unused extra instructions → ask (use them and go again / end as is / stop); all pass → `done`; a `fail` and returns left (one at first) → automatic return; else ask (accept / once more / stop; once more isn't offered without a reviewer). A return runs the last work stage again with the failed and unknown criteria and their evidence in a random-marker block "[What failed in the last review — reference]" (evidence 300 characters, `<` `>` full-width), not as user feedback; a meeting stage is redone by the lead alone, an approval stage doesn't wait for approval again. Then the check runs again. "Once more" raises the return limit by one. `done` is written only when every criterion is `pass` and no question is open; accepting otherwise ends `accepted` with the verdicts kept.
- **Waits**: two new hold reasons, `mission` (`kind: 'verdict'|'notes'`, round, the criteria left, unused notes, `more: false` without a reviewer) and `cap`, answered with the new `control` actions `accept` and `more` (or `stop`). Another action gets `{ ok: false }`. The goal is `waiting` meanwhile; the sidebar shows them as their own waiting kinds (`verdict`, `cap`).
- **Call cap**: each CLI start in a goal counts (`calls.used`, from the goal turn, including retries, takeovers, empty-answer retries and answers to questions). Before each work stage and the check, if `cap - used` is less than the stage's people, the run asks: 20 more / stop. The cap is 40 (`MISSION_CALL_CAP`); there is no setting yet.
- **Records**: the review answer keeps `review: { round, results: [{ id, verdict, evidence, text }], missing, retried }` and the block's span; the screen hides the block and shows a table marked "written by an agent · not confirmed by you". The goal keeps `round`, `returns`, `returnCap`, `calls`, and each criterion's `status`/`evidence`. Log lines for the check, the return, the questions and answers, the cap; a failing check line carries `fail: 'review'`, a check that hit a usage limit `fail: 'outside'`. Older data with `unreviewed` is read as an end state.
- The demo provider recognizes the check by its exact head and closing block example and answers with a block (`REVIEWFAIL`, `REVIEWFAIL2`, `REVIEWUNK` in the goal sentence change the verdict), so the flow can be tried at no usage.

## Consequences

- A goal costs at least one more call (two when the format has to be asked again), and a return costs the last work stage again plus another check.
- Not covered: the reviewer runs with its own permission setting; "don't change files" is an instruction, not enforced. To let it run tests, the user raises that agent's permission.
- Not covered: a reviewer from the same AI company as the workers is only flagged (the existing notice), not prevented.
- Not covered: the cap is checked before a stage starts; retries and takeovers inside a stage can go over it. Tokens and subscription percentage aren't capped, and there is no estimate before starting.
- Not covered: a goal cut by an app restart can only be discarded; continuing it is not built yet. The criteria can't be changed after confirming.
- Not covered: how reliably real CLIs write `oc-review` blocks, and how honestly they judge, is not measured; the tests use fake CLIs only.
- Not covered: only the last work stage is redone on a return; kept review stages after it don't run again. A meeting's return is one person's answer, not a new meeting.
