# 0014: Goal mode turns a request into a goal card the user confirms, and only the confirmed values become instructions

- Status: Accepted
- Date: 2026-11-19
- Related: [0006](0006-hire-proposal-in-chat.md) (a card in the chat the user approves), [0007](0007-local-only-user-messages.md) (what only a local model saw stays away from cloud AIs), [0009](0009-agents-ask-with-a-marked-block.md) (marked blocks at the end of an answer), [0013](0013-agents-keep-role-notes.md) (the injection check), `server/mission.js`, `server/orchestrator.js` (`send`, `missionProblem`, `#goalTurn`, `confirmMission`, `cancelMission`, `discardMission`, `#missionStage`, `#missionEnd`, `#prompt`, `recover`), `server/store.js` (`#fixStale`), `server/index.js` (session `PATCH`, `/mission/*`, `/proposals/:mid`), `server/providers/mock.js`, `public/js/views/mission.js`, `public/js/views/session.js`, `public/js/chat-tools.js` (`hideGoal`), `test/mission.test.js`

## Context

A team runs its stage list once and stops. Nothing says what "done" means, so a run can end with "the next step needs your approval" and the user can't tell whether the request was met. Making a team carry a request all the way needs, first of all, a goal and acceptance criteria the user agreed to, a step-by-step record, and later a fresh reviewer that judges each criterion. This record covers the first part: the goal card, and running the existing stage list with the confirmed goal attached.

## Options

1. Let the lead write the goal and start at once. Cheapest, but a wrong goal wastes everything after it, and text an AI wrote (possibly copied from a web page) would become an instruction to the agents that edit files.
2. Put a goal and criteria in each team's settings. Fixed per team, not per request.
3. A goal mode per session: the lead drafts a goal card from the request, the user confirms, edits or drops it, and only the values the user confirmed go to every stage as instructions.

## Decision

Option 3.

- Session fields: `goalMode` (boolean) and `mission`: `{ version: 1, id, status, phase: 'goal'|'work', request (first 2,000 characters), requestMsgId, leadId, goal, criteria: [{ id: 'c1', text, status: 'open', evidence: '' }], outOfScope, userDecides, notes: [{ id, text, at, used, msgId, files? }], cardMsgId, confirmedAt, editedByUser, log: [{ at, kind, text, msgId? }], createdAt }`. A session has one goal; a new goal replaces an ended one. The log keeps 200 lines; older lines are dropped and counted in one "n earlier lines left out" line.
- Status: `drafting` (the lead is writing the card) → `draft` (the card waits) → `active` → an end state: `unreviewed` (all stages ended; nobody has judged the criteria yet), `stopped`, `cancelled` (the card was closed, the goal turn failed, or a cut goal was discarded). `cut` means the app closed while the goal was running. `drafting`, `draft`, `active`, `waiting` and `cut` count as alive: while one is alive no new goal is made, and goal mode can't be turned off or the team changed (409). `waiting`, `done` and `accepted` are reserved for the review step and not set yet.
- Turning it on: `PATCH /api/sessions/:id { goalMode }`. It is refused with 400 and the reason for a session without a team, for a team that mixes models on this PC with cloud AIs (an agent with automatic routing counts as either, so it mixes with a local-model agent; a team of only local models is allowed), and for sessions started by a schedule or a board card. The same check runs again when a request becomes a goal and when a card is confirmed. Changing the team of a goal-mode session to one that fails the check turns goal mode off.
- Which messages: in a goal-mode session, a message without an `@name`, not a handoff request and not from a schedule is looked at before "interrupt now" and before hire detection. With no alive goal it becomes a goal turn; with a waiting card that card is closed and a new goal turn starts; with a running goal it becomes an extra instruction; with a cut goal it gets 400. While the card is being drafted, "interrupt now" still goes to the lead. If another run is going, the request waits in the queue (`mission: true` on the message) and starts as a goal turn when its turn comes.
- Goal turn: a run with one stage and the lead alone. The lead is the chair of the team's first meeting stage, else the first member whose role is analysis, else the first agent of the first stage. The prompt tells it not to start the work and to write a goal (one line), 2 to 7 criteria that can be checked by opening a file or running a command, what is out of scope and what only the user can decide, ending the answer with one fenced `oc-goal` JSON block. The block is read only when it is the last thing in the answer (as in 0009). Values are cleaned: one line, control and invisible characters removed, the goal up to 200 characters, criteria up to 300 characters and 7 items, the other lists up to 5 items of 200 characters. A block with one criterion is accepted. If no block can be read, the lead is asked once more in the same run; if that fails too, the card uses the first 200 characters of the request as the goal and has no criteria, with a notice. The lead may ask the user with `oc-ask`. An error or a stop closes the goal without a card. The lead's draft answer (`goalDraft`) is left out of what is passed to other agents and out of project memory; the screen hides the block's span (`goalBlock`).
- Goal card: a message `{ role: 'proposal', kind: 'goal', status: 'open'|'confirmed'|'cancelled', text: '', missionId, leadId, goal, criteria, outOfScope, userDecides, warn?, fallback?, confirmed?, edited? }`, kept out of what agents get, like the hire card of 0006. The injection check of 0013 runs over the draft; a hit puts a warning on the card and does not block. `POST /api/sessions/:id/proposals/:mid` refuses every card whose kind is not `hire` (409).
- Confirming: `POST /api/sessions/:id/mission/confirm { missionId, expected, edited? }`. `expected` is the card the screen showed; its goal, criteria, out of scope and user-decides lists must all match the stored draft character by character, or the answer is 409 with the current draft and the screen redraws it. It is also 409 for another goal's id, a goal that is not `draft`, a run in progress, a card that is not the session's latest goal card, and a card followed by any user message. It is 400 when the goal or the criteria are empty, or the team check fails now. `edited` holds the user's values (cleaned the same way) and sets `editedByUser` when they differ. Nothing waits after the body is read, so a double click confirms once. `POST …/mission/cancel` closes a waiting card; `POST …/mission/discard` closes a cut goal.
- Work: one run with the team's stage list, run as before (meetings, approval and error gates unchanged). Stages in which every agent has a review role are left out, with a line in the log saying criteria judging replaces them; if that would leave no stage, nothing is left out. Every stage prompt starts with `[Confirmed goal and acceptance criteria (confirmed by the user. Don't change them)]`: the goal, the numbered criteria and what is out of scope. Those are the only goal values given as instructions, and the run uses the values held in memory from the moment of confirming. When all stages end, the goal is `unreviewed`, not done; a stop or an internal error makes it `stopped`.
- Extra instructions: a message sent while the goal runs is stored as a note and as a user message marked `missionNote` (stored in project memory like any message), is left out of the earlier conversation, the missed conversation and the whole-conversation file, and goes into every stage that starts after it under `[Additional user instructions]` (marked `used`). Notes that came after the last stage started are counted in the log. An instruction sent to one agent from its panel goes in directly as before and gets a log line.
- Restart: when a session is read from disk, `drafting` becomes `cancelled` and `active` or `waiting` becomes `cut`, each with one chat line at start. Nothing starts again by itself. A waiting card stays and can be confirmed.
- Order and models: the order (goal turn, then the stage list) is fixed in code. Each agent keeps its own model and the user's overrides; no router picks models by how hard a task looks.
- The event `mission { sessionId, goalMode, mission }` is sent on every change (the session summary event doesn't carry these fields). The demo provider recognizes the goal turn and answers with a block, so the flow can be tried with the demo team at no usage.

This adds `goalMode` and `mission` to sessions, `kind: 'goal'` cards, and `missionNote`, `goalDraft`, `goalBlock` on messages and `mission`, `missionId` on runs. Older versions ignore them.

## Consequences

- Each goal costs one AI call before the work starts (two when the block has to be asked for again), plus any question the lead asks.
- A user message after the card, even one to `@name`, makes that card unusable; the user sends the request again. Clearing the conversation drops the goal.
- Not covered yet: judging each criterion with a fresh reviewer, one automatic return for fixes, a cap on calls per goal, and continuing a cut goal (it can only be discarded). Research, meetings planned by the lead and task cards are not part of goal mode; the team's stage list runs as it is.
- Not covered: the criteria can't be changed after confirming (drop the goal and send the request again); goal mode isn't available in scheduled runs, board cards, or teams that mix local models with cloud AIs.
- Not covered: how reliably real CLIs follow the `oc-goal` format is not measured; the tests use fake CLIs only.
- Not covered: the lead keeps its draft in its own resumed CLI conversation; the confirmed block in each prompt is what counts.

- To undo: drop the goal branch in `send` and the `goalMode` handling in `PATCH`; stored `mission` fields are then ignored.
