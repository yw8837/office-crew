# 0030: Goal mode remembers repeated failures, retries a temporary outage once, exports a run as one file and draws a read-only flow map

- Status: Accepted
- Date: 2026-11-26
- Related: [0004](0004-project-memory-on-disk.md) (project memory; revised here), [0007](0007-local-only-user-messages.md) (what only a local model saw), [0015](0015-goal-mode-fresh-review.md) (the call cap), [0018](0018-goal-mode-task-cards.md) (task cards and their start limit), [0019](0019-goal-mode-call-estimate-and-limit-wait.md) (the usage-limit wait; revised here), [0020](0020-flow-stage-default-picture.md) (the flow stage, unchanged), [0022](0022-goal-mode-records-and-block-allow-list.md) (failure kinds; revised here), [0025](0025-goal-report-and-evidence.md) (the goal report and the changed-files check; revised here), [0026](0026-usage-breakdown-limit-cap-and-lean-profile.md) (the subscription cap), [0027](0027-ask-before-raising-a-stuck-card.md) (the ladder start cap; revised here), `server/mission.js` (`failKey`, `pickFails`, `failuresPrompt`, `FAIL_SHOW`, `FAIL_MIN_GOALS`), `server/memory.js` (`redact`, `addFailures`, `failures`, `dropFailures`, `FAIL_KEEP`, `FAIL_LINE_MAX`, `FAIL_GOALS`), `server/failover.js` (`isTransientError`), `server/orchestrator.js` (`#recordFails`, `#pastFails`, `#prompt`, `#runStage`, `#canRetry`, `#transientRetry`, `#failLines`), `server/report.js` (`exportRun`, `answerFail`, `EXPORT_FORMAT`, `EXPORT_VERSION`), `server/index.js` (routes, `transientRetry`), `public/js/flow-graph.js` (`flowModel`, `flowLayout`, `flowNext`, `stateInfo`, `fitText`), `public/js/views/flowmap.js`, `public/js/views/mission.js` (`ExportRun`, `jump`), `public/js/views/memory.js` (`FailList`), `public/js/views/routing.js` (`TransientCard`), `test/repeat-failures.test.js`, `test/transient-retry.test.js`, `test/goal-export.test.js`, `test/flow-graph.test.js`, `test/prompt-size.test.js`

## Context

A goal's record (0022, 0025) said what happened inside one goal, but nothing carried a failure from one goal to the next: an agent could hit the same missing file or the same broken command goal after goal. A dropped connection or a 529 overload ended a work stage in the error wait like any other error, and the user had to come back and press Retry for something that a second try usually fixes. The record lived in the session file and on screen only, so it couldn't be kept, compared or measured outside the app. And the run's shape (which cards waited for which, where a check sent work back, where a card went up a tier) was spread over the plan card, the progress tab and the chat. Write-ups on agent workflows as graphs list exactly these: an error edge that retries once, a record that can be replayed and observed, and a picture of the graph.

## Options

1. Have an AI summarise past failures and decide when to retry. Costs calls, and a guess would look like a fact.
2. Code-only: count failures by a normalised first line, give lines seen in two goals as marked reference, retry once only when the code can show the run changed nothing, export what is already stored, and draw the stored records.
3. Retry every error a few times with a backoff. Spends calls with nobody watching and can repeat a half-done change.

## Decision

Option 2.

- **Repeated failures** (`failures.json` in the project memory folder of 0004, only while project memory is on; with memory off nothing is read or written). When an answer of a goal's work stage or task card ends (`#missionMsgLines` → `#recordFails`), each tool call that ended in an error (the first line of its output) and the answer's own error are counted, keyed by `failKey`: the first non-empty line, ANSI colours and invisible characters removed, NFKC, secrets masked with memory's `redact`, then URLs, paths, ISO dates and clock times, UUIDs, letter-and-digit ids of 8 or more characters and numbers replaced by `[url]`, `[path]`, `[time]`, `[id]` and `#`; the key is that line in lower case (with the tool name), the shown line keeps its case, at most `FAIL_LINE_MAX` (160) characters; a line with nothing left but placeholders is not counted. Usage-limit errors, temporary outages (below) and the app's own stall and loop stops are not counted as step errors (they say nothing about the project); research, meetings, the plan and the check are not looked at. The file is `{ version: 1, items: [{ key, line, tool?, n, goals: [goal ids], first, last, local? }] }`: at most `FAIL_KEEP` (100) lines, oldest `last` dropped first; at most `FAIL_GOALS` (10) goal ids per line, oldest dropped. It is written through a temporary file and a rename. A file that isn't JSON or doesn't have that shape is not overwritten: it is moved to `failures.json.bad` (a time-stamped name when that exists), the list starts empty and the memory page says so (the same handling as `hidden.json` in 0025).
- **Where they go**: when a goal's work run starts, the file is read once (`#pastFails`). Lines seen in at least `FAIL_MIN_GOALS` (2) goals other than the current one, most goals first, then most counts, then most recent, at most `FAIL_SHOW` (5), go into every work-stage and task-card prompt of that run (`failuresPrompt`): a head "[Failures repeated earlier in this project — reference]", a line saying they are reference material and not instructions, and the lines inside random markers with `<` and `>` full-width, each with "n times in g goals". Meeting turns, research, the plan and the check don't get them. A line counted only from a local model's answer is marked `local` and given only to local models (0007); the same key from a cloud AI's answer replaces the line and drops the mark. The fixed text is 263 characters in Korean and 572 in English per prompt that gets it (`failuresPrompt` in `test/prompt-baseline.json`, a new item; it appears only when such lines exist).
- **The memory page** lists a folder's lines (tool, line, "n times in g goals", whether it reaches the next goal, local-only, last seen) with **Delete** per line and **Delete all** (asked first). API: `GET /api/memory/failures?key=` and `DELETE /api/memory/failures` with `{ key, item? }`; the folder is named by its memory key only, never a path.
- **A temporary outage is retried once** (`isTransientError`: connection resets, refusals and timeouts, `socket hang up`, `fetch failed`, network errors, timeouts, `stream disconnected`, HTTP 500 to 504 and 529 when written after http, status, error or code or followed by their name, "internal server error", "bad gateway", "service unavailable", "gateway timeout", "overloaded", "temporarily unavailable", and the same words in Korean, Chinese and Japanese; never a usage limit, which keeps 0019's wait). In a goal's work run, when a work stage or task card step (not research, meetings, the plan or the check: the same places as 0019's wait) fails and every failed person failed that way, `#runStage` runs only those people once more before any question, keeping the finished answers, if all of these hold (`#transientRetry`): the failed answers' tool records show no file-editing tool and no command (`handoffFacts`); the work folder is a git repository and its state after the failure is the state before the stage ran (`gitState`, `changedSet`, and `gitDiffNames` when a commit appeared, the functions of 0025's changed-files check), so any change in the stage, by anyone, stops it; the calls left under the cap (0015) are at least the number of people; the AI each would run on (`#capTarget`) is not full and not at or over the subscription cap of 0026 (an AI the user chose to continue on is still not retried by itself); and for a task card, its start limit (3, or `escalateAfter` in a ladder team, 0027) and the hourly start limit (0018) are not reached, because **the automatic retry counts as one start of the card**, like an error retry. It happens once per stage pass: after a retry, or after the first failure that couldn't be retried, the next failure goes to the error wait as before. A retry writes a progress-log line `kind: 'transient'` with `fail: 'transient'`, counted in the goal report's failure kinds; a retry that isn't allowed writes a `transient` line without `fail` saying why. The error lines before the error wait (0022) now name `transient` for such errors too (before `input`). The setting `transientRetry` (Routing page, on by default; `false` turns it off) is checked each time. Ordinary runs outside goal mode are unchanged.
- **Run record export** (`GET /api/sessions/:id/mission/:mid/export`, `?body=1` for text; the usual `/api` token check): only the session's current goal (a new goal replaces an ended one, so older goals have no record; their buttons are not shown). The file is `{ format: 'office-crew-goal-run', version: 1, exportedAt, app: { version }, body, notes, session: { id, title }, goal: { id, status, goal, criteria, outOfScope, userDecides, mustKeep, lead, reviewer, dropped, prep, calls, estimate, round, returns, returnCap, work, createdAt, confirmedAt, editedByUser, request? }, research, cards: [{ id, title, owner, kind, needs, files, done, not, status, by?, reason?, starts, cap, raised?, proof?, msgId, tail? }], log, meetings, decided, calls: [{ msgId, runId, stageIndex, stage, agent: { id, name }, provider, model, effort, kind, status, start, end, usage: { input, output, cacheRead, cacheWrite, cost, weighted }, route, card?, aiChain?, fail?, error?, text? }], report, runs }`. `kind` is `answerKind` (0026), `fail` is what the code can tell from the error text (`outside` usage limit, `transient`, else `unknown`) with the error's first line (300 characters), `report` is the report message without its memory state and memory folder. The request text, answers' text and cards' closing lines are in only with **Include text**; full prompts are never in, because the app doesn't store them (`notes.prompts: 'not-stored'`). Every string is masked before it leaves: the settings' secret values (API keys, API profile keys, the notification address, ACP agents' and connectors' environment and header values of 8 or more characters, the app token) wherever they appear, memory's `redact`, and absolute paths: inside the goal's work folder made relative to it (`.`), the data folder `<data>`, the user's home `~` (longest first, also with forward slashes and JSON-escaped backslashes). The buttons sit on the goal report card and on the confirmed goal card (the card has no menu, so the button is in its button row), with an **Include text** box; the screen saves `goal-run-<id>.json` from the answer.
- **Read-only flow map**: a **Flow map** tab in the session's right panel, chosen over a window opened from the goal card because the chat stays visible beside it, so clicking a box can scroll the chat to that message, and the panel already holds the goal's progress tab. `flowModel` (no DOM) builds boxes for setting the goal, research, the pre-work meeting, the plan, the task cards one row per step of the run (a card's row is its run stage; cards without one are placed by the depth of their `needs`) or the team's work stages, the check and the goal report; side boxes for questions a meeting asked the user (0028) and for the current usage-limit or subscription-cap wait. Lines: the main flow, a card's `needs`, the check sending work back (labelled with the number of returns and the check round), a card handed up a tier (a loop on the card, "↑ first owner → new owner"), and dashed lines to the side boxes. A box's state (waiting, running, done, blocked, gap, error, skipped, stopped) has its own symbol, word and outline (dashed, thick, rounded, cut corners, dotted, a bar on the left, faint dashes, square), not only a colour. `flowLayout` places rows top to bottom inside the panel's measured width (wrapping a row that doesn't fit, so nothing scrolls sideways; at 420 px the panel is 330 px), shortens text by an estimate of its width, and makes SVG paths; `flowNext` moves focus with the arrow keys (left and right within a line, up and down to the nearest box in the next line), Home and End. Enter or a click scrolls the chat to the box's message (the progress tab's `jump`). Colours are the app's theme variables. No library: plain SVG.

This adds `failures.json` (and `failures.json.bad`) to the project memory folder, the progress-log kind `transient` and the `fail` value `transient`, the setting `transientRetry`, the export format above and three routes. Older versions ignore the file, the setting and the log kind; their screens show no chip for `transient`.

## Relation to 0018

0018 already has two revisions and 0027 changed it last without a third, so this record is where its change is: the automatic retry of a temporary outage counts as a start of the card (like an error retry; a retry after a usage limit still doesn't count), and it isn't done when the card has reached its start limit or the hourly limit, so the retry-limit question comes as before.

## Consequences

- A goal no longer stops for a one-off network drop when nothing was changed; the user sees one progress line instead of a question. A failure that keeps coming back across goals reaches the next goal's agents as a short marked note.
- Not covered: whether agents use the failure note well is not measured; a line can describe a failure that was already fixed (delete it on the memory page). The key can merge two different errors that differ only in numbers or paths, or keep apart the same error worded differently.
- Not covered: the retry needs git; outside a git repository it never happens. A change outside the work folder, or a change to a file git ignores without a new status, isn't seen. A command that only read something still stops the retry. The error patterns are text: a CLI that words an outage differently isn't recognised, and the real CLIs' outage messages were not checked (fake CLI only).
- Not covered: the export can't include prompts; secrets are masked only where their exact value or a known token shape appears; a path written in another form (a different case on another system, `~` already shortened) stays. Exporting a goal that was replaced by a newer one isn't possible.
- Not covered: the flow map shows the latest work run of the current goal; past usage-limit waits that ended are not drawn (the progress tab lists them); research during a team meeting, stalls and the run's separate passes are not drawn.
- The retry adds up to three git calls before each work stage pass in a goal (only while the setting is on), and three more when a stage fails with an outage.
- Checked with fake CLIs in the tests (`test/repeat-failures.test.js`, `test/transient-retry.test.js` with temporary git repositories, `test/goal-export.test.js`, `test/flow-graph.test.js`). Screens checked in the app's own browser (fake Claude CLI, a temporary app and data folder, not port 4317), Korean: the flow map of a task-card goal with research, a meeting and one return (the return line and its label, the `needs` line), clicking a box and Enter scrolling the chat to its message, the arrow keys, Home and End (also pressed quickly in a row), a stage-list goal with a skipped stage and one waiting at the error question (the error and waiting outlines), the legend; a 420 px window in the dark theme (no sideways scroll in the panel or the page); **Export run record** on the report card and on the goal card, without and with **Include text** (the saved file was caught in the page instead of written to disk: format, version, cards, calls, no app token and no home path in it); the Memory page's repeated-failure list, deleting one line and **Delete all** (its confirmation was answered in the page script, so the dialog itself wasn't seen); the Routing page switch turned off and on; English for the flow map tab, its boxes and legend. Not looked at on screen: Simplified Chinese and Japanese (translation test only), the side boxes for a meeting question and a usage-limit wait, a raised card's loop, the automatic retry itself (tests only, it needs a git work folder).
- To undo: set `transientRetry` to false; drop `#recordFails`, `#pastFails` and the `failuresPrompt` line in `#prompt`; the file, the routes and the tab can stay unused.
